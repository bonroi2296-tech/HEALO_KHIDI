# 데이터 주권·보안 체계 (HEALO KHIDI)

> **목적**: "외부 서비스(Supabase·LiveKit·Gemini 등)를 쓰는데 환자 데이터 주권은 괜찮은가?"에 대한 단일 답변 문서. KHIDI 중간평가(①사업목적·BM / ②추진실적 / ③향후계획 / ④성과지표) 중 **"ICT 체계 구축"** 정성 근거로도 사용.
>
> 갱신일: 2026-06-29 · SoR(이 영역의 기준 문서). 보안 핵심 규칙 자체는 `docs/SECURITY_CHECKLIST.md`.

---

## 0. 한 줄 요약

환자 정보는 **한국(서울) 리전**에 저장되고, 민감정보(PII)는 **우리만 가진 키로 AES-256-GCM 암호화**돼 있어 인프라 제공사(Supabase 운영자 포함)도 평문을 못 본다. 즉 **"외부 서비스 = 잠긴 금고의 보관소"**일 뿐, 데이터 통제권은 우리에게 있다. 외부 서비스를 자체 개발(self-host)하지 않아도 주권의 핵심(위치·암호화·접근통제)은 충족된다.

---

## 1. 우리가 쓰는 외부 서비스와 주권 관점

| 서비스 | 역할 | 환자 PII 접촉 | 주권 통제 수단 |
|---|---|---|---|
| **Supabase** (PostgreSQL) | DB·인증·파일저장 | 저장 (암호화됨) | 서울 리전 + 앱단 AES-256-GCM(우리 키) + RLS |
| **LiveKit** | 원격협진 영상(WebRTC) | 영상은 실시간 스트리밍 전송 | 초대 토큰 기반 입장. 녹화본 저장 시(`recording_url`) 접근통제된 저장소 경유 |
| **Google Gemini** | AI 채팅 답변·임베딩 | 환자가 타이핑한 자유텍스트 | **전송 전 식별자 마스킹**(본 문서 §3) |
| **Vercel** | 호스팅(앱 실행) | 일시 처리(메모리)·저장 안 함 | 비밀키는 env, PII 영속 저장 없음 |
| **Resend / AWS SES** | 이메일 발송 | 수신자 주소·본문 | 최소 정보만, 발송 목적 한정 |
| **Sentry** | 에러 모니터링 | 의도적 미수집(스크럽) | 메시지 본문/PII 전송 금지 규칙 |

## 2. 저장 데이터 주권 — 위치·암호화·접근통제 (이미 확보)

### 2-1. 데이터 위치 (Data Residency)
- Supabase 프로젝트 리전 = **`ap-northeast-2` (서울)**. 환자 정보가 물리적으로 **한국 내**에 위치 → 국외 반출 아님.

### 2-2. 암호화 (Encryption at rest, 앱단)
- 환자 PII(이름·이메일·연락처 등)는 **AES-256-GCM**으로 암호화 후 `*_encrypted` 컬럼에 저장.
  - 모듈: `src/lib/security/encryptionV2.ts` (`encryptStringNullable()` 등), 키: `ENCRYPTION_KEY_V*` (버전드 키 회전 지원).
- 핵심: 키는 **우리 환경변수에만** 있고 DB에 없다 → DB 덤프가 유출돼도, **Supabase 운영자가 들여다봐도** 우리 키 없이는 평문 복원 불가. = 실질적 데이터 통제권은 우리에게.

### 2-3. 최소 노출 (Least exposure)
- 어드민 **목록** 화면은 마스킹값(`j***@gmail.com`, `홍**`)만 표시, **상세** 진입 시에만 복호화. (`src/lib/security/maskPii.ts`)

### 2-4. 접근통제 (Access control)
- `inquiries` 등 민감 테이블은 **service_role 서버 전용** — 브라우저 직접 쿼리 금지, 서버 API 경유.
- 새 API는 인증 헬퍼 필수(`requireAdminAuth` / `requireConsultationAccess`), 권한은 `app_metadata.role` 기준 + RLS 정책.

## 3. AI 전송 주권 — 빈틈 보완 (본 작업에서 추가)

### 문제
DB는 한국·암호화인데, 공개 채팅에서 **환자가 직접 타이핑한 자유텍스트**는 답변 생성을 위해 외부 LLM(Gemini)으로 전송된다 → "저장은 잠겨있는데 AI 입력만 국외 평문"이라는 비대칭이 있었다.

### 조치
모델로 보내기 **직전**, 환자 텍스트의 **고신뢰 식별자**를 토큰으로 가린다.
- 모듈: `src/lib/security/redactModelPii.ts` (server-only) + 회귀 테스트 `redactModelPii.test.ts`.
- 가리는 대상: **이메일 · 전화번호(국제/국내) · 주민등록번호 · 여권번호.**
- 적용 지점(중앙화): `src/lib/chat/generateReply.ts` 의 `generateChatReply`·`streamChatReply` — RAG 임베딩·답변 생성·judge·서버 로그 전 경로가 마스킹본을 사용. 공개/환자 채팅 3개 진입점 모두 이 함수를 거치므로 일괄 적용.
- 의료 본문(증상·암종·질문)과 일반 숫자(금액·날짜)는 **보존** → 답변 품질 영향 없음.

### 의도된 한계 (솔직 고지)
- **사람 이름은 가리지 않는다**: 자유텍스트에서 이름은 병명·일반 단어와 구분이 어려워 오탐 위험이 크다. 대신 이름은 의료 답변 품질 영향이 적고, DB 저장 시점엔 암호화로 보호된다.
- **원격협진 STT·요약·실시간 번역**(`/api/khidi/consultation/*`)은 의사-환자 임상 대화 자체를 처리하는 게 목적이라 마스킹하지 않는다. 이는 **예약된 상담 안에서의 동의 기반(consent-based) 처리**다. (향후: 처리 동의 고지 문구 점검 권장.)

## 4. "전부 자체 개발(self-host)" 검토 결론

기술적으로 Supabase·LiveKit·Sentry 등은 오픈소스라 자체 운영이 **가능**하나, 1인 운영 + 정부과제 상황에서는 **권장하지 않는다**:
- **운영 부담**: DB 백업·보안패치·24시간 장애대응을 혼자 떠안게 됨 → 오히려 보안 *리스크* 증가.
- **비용**: 소규모에선 직접 서버 운영이 외부 서비스보다 비쌀 수 있음.
- **평가 관점**: 인프라 자체 구축은 성과지표(유치/상담)에 안 잡힌다. "검증된 글로벌 인프라 위에 ICT·보안 체계를 구축"하는 편이 평가·실적 모두에 유리.

대신 **자체 개발이 아니라 통제권 확보**에 집중: ①한국 리전 ②우리 키 암호화 ③접근통제 ④AI 전송 마스킹. 위 4가지로 데이터 주권의 핵심은 충족된다.

## 5. 향후 점검 항목 (선택)
- [ ] 원격협진 임상대화 AI 처리에 대한 환자 동의 고지 문구 점검.
- [ ] 외부 서비스 lock-in 회피: DB는 표준 PostgreSQL이라 이전 가능, 인증·스토리지 의존도 주기적 점검.
- [ ] 키 회전(`ENCRYPTION_KEY_V*`) 운영 절차 문서화.
