## 0. 한 줄 결론

**카피 가능하다. 단 「그대로」는 안 된다 — 그들 모델의 심장은 우리에게 없는 B2C 트래픽이고, 우리 심장은 그들이 아직 못 만든 것(운영·전환·측정)이다.**

베낄 것은 **상품 포장·가격 구조·계약 절차**이고, 베끼면 죽는 것은 **"우리가 환자를 데려다준다"는 약속**이다. 우리는 유입이 아니라 **전환과 운영**을 판다.

### 1-1. 상품은 두 층이다

| | **Starter Tech Plan** (도구) | **Scale-up Plan (PB형)** (성과 동행) |
|---|---|---|

### 1-2. 계약 절차 (우리가 그대로 베낄 부분)

`전자계약서 서명 → 세금계산서·입금 → 구축 폼 작성·데이터 세팅 → 검수 후 오픈(약 4주)`
필요 서류는 **사업자등록증 사본 + 서명용 이메일** 딱 둘. 병원 담당자가 부담을 못 느끼게 설계돼 있다. **이 4단계는 그대로 쓸 만하다.**

### 1-3. 그들의 컨설팅 상품 (P0~P6)

시장 선정 → 경쟁사 분석 → 환자 페르소나 → 키워드 리서치 → 콘텐츠 갭 → **연 365개 아티클 타이틀** → 아웃라인·집필. 목표치는 `연 365건 / 키워드 400개 / 월 트래픽 +15% / 인바운드 전환 3.0%`.

**솔직한 평가: 이 뼈대는 잘 만들었다.** 병원 입장에서 "뭘 받는지"가 명확하다. 우리 제안서도 이 정도의 **눈에 보이는 산출물 목록**이 필요하다.

## 2. 그들 자료에서 찾은 균열 (= 우리가 들어갈 틈)

### 2-1. 🎯 그들의 우선순위에 「암·한방·러시아」가 없다

제안서 p7 자기들 데이터다.

**진료과별 유입 비율**: 성형·피부·줄기세포 **40%** / 안과 19% / 건강검진·정형 14% / 치과 12% / 여성질환 10% / **한의원 5%(최하위)**

**진료과목별 단가**: 줄기세포 3,000만 > 성형 1,500만 > 정형 1,000만 > 외과 900만 > 안과 500만 > 피부 400만 > 산부인과 300만 > 치과 200만 > 건강검진 150만 > 내과 100만 > **한방 50만원(최하위)**

**환자 국가 비율**: 미국·영어권 **45%** / 일본·중국 20% / 동남아 15% / 몽골·중동 20% → **러시아·CIS가 항목에 아예 없다.**

> **판정**: CloudHospital은 **고단가 미용·줄기세포 + 영어권**에 최적화된 기계다. 한방은 그들 표에서 유입 꼴찌(5%)·단가 꼴찌(50만원)다.
> **면력한방병원이 저기 들어가면 우선순위 맨 뒤에 선다.** 반대로 **우리는 그 버려진 칸(중증·암·한방·러시아어권)에 이미 3년치 콘텐츠와 병원망을 깔아놨다.**

### 2-2. 성공사례를 뒤집어 보면

D병원 사례(4개월): 진료 요청 **30건** → 실제 방문 **7건**(전환 23%) → 객단가 3,000만원 → 매출 2억.

- 병원이 4개월에 실제로 받은 환자는 **7명, 월 1.75명**이다.
- 매출 2억이 나온 건 **객단가가 3,000만원(줄기세포)이었기 때문**이다.
- **한방 단가 50만원(그들 표)에 이 전환율을 그대로 곱하면 4개월 매출 350만원**이다. 같은 기계, 다른 결과.

> **이 계산은 우리 제안서의 무기이자 우리 자신에 대한 경고다.** 유치 사업의 성패는 「몇 명」이 아니라 「단가 × 전환」이다. **암 치료는 단가가 2,000~4,000만원대**(우리 사업계획 기준)라 이 모델이 성립한다. 한방 단독은 안 된다 — **양·한방 협진(면력 + 협진 대학병원)으로 묶어야 단가가 선다.** 우리가 이미 그 구조다.

### 2-3. 숫자가 자료마다 다르다

| 항목 | 제안서 | 그들 웹사이트 |
|---|---|---|
| 제휴 병원 | 연혁 **7,000개** / 파트너십 페이지 **+200개** | 7,000+ |
| 플랫폼 방문 | **월 80만명** | **월 15만명** / 연 480만 |
| 등록 병원 | **12만개** | 수천 |

같은 문서 안에서 제휴 병원이 7,000과 200으로 갈린다. **층위가 다른 숫자(등록·제휴·활성)를 섞어 쓴 것으로 보이지만, 병원이 실사하면 바로 걸리는 지점이다.**
→ **우리는 반대로 간다: 숫자는 적게, 대신 전부 검증 가능하게.** (우리 실측치는 §3)

### 2-4. 🔬 dekabi.com 해부 — 그들이 실제로 만들어주는 결과물

그들이 구축한 실물 사이트를 직접 긁어서 측정했다.

**잘한 것 (배울 점)**
- **51개 로케일** 실제 구동(`en-US, ru-RU, kk-KZ, mn-MN, uz-UZ, az-AZ, ka-GE, ky-KG …` CIS·중앙아시아 포함). 러시아어판은 **서버에서 러시아어로 렌더**된다 — 크롤러에게도 보인다.
- **AI 봇 정책이 정교하다.** 학습용 수집봇(GPTBot·ClaudeBot·Bytespider·Meta-ExternalAgent)은 **차단**하고, 답변용 검색봇(OAI-SearchBot·PerplexityBot·ChatGPT-User·Claude-SearchBot·Google-Extended·Applebot)은 **허용**한다. *"AI 답변엔 나가되 학습 데이터로는 안 준다"* — 우리보다 한 수 위다. **우리도 이 구분을 도입해야 한다.**
- `llms.txt` 보유, 구조화데이터(`MedicalClinic`·`FAQPage`·`Question`/`Answer`·`OpeningHours`) 적용.

**못한 것 (우리가 이기는 지점)**
- **`hreflang` 태그가 0개다.** 51개 언어판이 있는데 **서로 연결하는 표시가 없다** → 구글이 "같은 페이지의 51개 언어판"으로 못 묶는다. 다국어 SEO의 가장 기본이 빠졌다. (홈·러시아어판 둘 다 0. 대소문자 무시하고 재측정해서 확인함.)
  - **우리(healwith)는 6개 + `x-default` = 7개가 정상 출력된다** — 실측 확인.
- 사이트 구조가 **얕다**: 소개·의료진·후기·아티클 위주. 우리가 가진 **암종 → 병기 → 병원 → 예후 → FAQ** 같은 깊은 축이 없다.
- 이미지·리소스가 `icloudhospital` 도메인에 매여 있다(396회 참조). **병원이 자기 자산을 온전히 소유하지 못한다.** 계약이 끝나면 뭐가 남는지 불분명 — **우리 제안서의 「자산은 병원 것」 조항이 여기서 힘을 받는다.**

### 4-3. 🔑 우리만의 결정적 무기 — 「측정」

CloudHospital은 *"SEO + GEO(생성형 AI 검색) 대응"*을 팔면서 **효과를 재는 숫자를 안 준다.** 병원 사장 입장에서 가장 큰 불안은 *"돈 냈는데 진짜 되는 거 맞아?"* 다.

**우리는 그걸 이미 숫자로 잰다.** 환자 질문을 실제로 AI에 물어보고 우리가 인용되는지 날짜별로 쌓는 도구가 있다(`scripts/aeo-visibility.mjs`).

- **현재 우리 기준선은 인용 0/9로 낮다.** 이건 제안서에도 숨기지 않는다.
- 오히려 이렇게 판다: *"시작점이 0인 것부터 보여드립니다. 매달 이 숫자가 어떻게 움직이는지 같이 봅니다."*
- **투명한 0이, 검증 안 되는 「+55%」보다 병원에게 더 신뢰를 준다.**

### 4-4. 그들에게서 그대로 베낄 것

1. **계약 4단계**(전자계약 → 입금 → 구축 폼 → 검수 오픈, 4주) — 병원 담당자 부담이 낮게 설계돼 있다.

# 10. 「판에 찍어내기」 로드맵 — 단기·중기·장기

## 10-0. 공장화의 유일한 성적표

**「병원 1곳을 늘리는 데 며칠 걸리나」** — 이 숫자 하나로만 판단한다. 기능 개수·코드 줄 수는 성적표가 아니다.

| 단계 | 목표 소요 | 사람이 붙는 시간 |
|---|---|---|
| 지금 | (해본 적 없음 — 추정 3~4주) | 거의 전부 |
| 2단계 끝 | 2~3주 | 대부분 |

## 10-1. 먼저 — 「판을 먼저 만들면 안 되는」 이유

**판은 미리 못 만든다.** 1~2곳을 손으로 만들어봐야 *무엇이 반복이고 무엇이 병원마다 다른지* 알 수 있다. 지금 상상으로 판을 만들면 **아무도 안 쓰는 설정 항목 50개짜리 판**이 나온다. (우리가 이미 겪은 부류다 — 병원 포털 콘텐츠 기능은 만들어놓고 `HOSPITAL_CONTENT_ENABLED = false` 로 꺼져 있다. 쓸 곳이 정해지기 전에 만든 것.)

**규칙: 손으로 두 번 한 것만 판에 새긴다.**

## 10-2. 무엇을 자동화해야 하는지 — 실측으로 확정

환경 열쇠 142개를 성격별로 갈랐다.

| 성격 | 개수 | 병원 추가 시 |
|---|---|---|
| 우리가 공용으로 쥠(AI·지도·번역 키) | 10 | **안 건드림** |
| 기능 스위치·플랫폼 자동주입 | 12 | **안 건드림** |
| 테스트·개발 도구 | 15 | **안 건드림** |
| 기타(AI 한도·감시·폰트 등, 기본값으로 충분) | 41 | **대체로 안 건드림** |
| **병원마다 새로 필요** | **64** | ← 여기만 해결하면 된다 |

그 64개를 다시 가르면 **길이 두 개로 갈린다.**

| | 항목 | 개수 | 어떻게 없애나 |
|---|---|---|---|
| 🤖 **기계가 만들 수 있다** | 보안 열쇠 15 · DB 8 · 화상(LiveKit) 4 · 주소 4 · 운영자 5 | **36** | 설치 스크립트가 **랜덤 생성 + 외부 서비스 API 호출**로 자동 발급. 사람 입력은 「병원 이름·도메인」 2개면 파생된다 |
| 🖐 **사람이 외부에 신청해야 한다** | 상담 채널(WhatsApp 비즈니스 번호 승인·텔레그램 봇·라인·위챗) 16 · 메일 도메인 인증(SPF/DKIM) 12 | **28** | 코드로 못 줄인다 → **신청 대행 체크리스트 + 병원이 서명할 위임장 양식**으로 줄인다 |

> **핵심 판단**: 판에 찍기의 진짜 병목은 코드가 아니라 **바깥 승인 절차(WhatsApp 번호·메일 도메인)**다. WhatsApp 비즈니스 번호 승인만 보통 며칠~2주다.
> → **3단계에서 코드 자동화(36개)를 끝내면, 남는 건 전부 「기다리는 시간」이 된다.** 그때부턴 **신청을 계약 첫날 동시에 걸어두는 순서 설계**가 공기를 줄인다.

## 10-3. 그리고 — 진짜 시간을 먹는 건 열쇠가 아니라 「콘텐츠」다

솔직히 말하면 열쇠 64개는 며칠짜리다. **6개 언어 의료 콘텐츠가 몇 주짜리다.** 병원이 바뀌면 암종·시술·의료진·가격·후기가 전부 다르다.

**다행히 우리는 여기가 이미 반쯤 자동이다.**

| 이미 있는 것 | 판에서 하는 역할 |
|---|---|
| 문구 편집기(덮어쓰기 202건·이력 247건) | 콘텐츠가 **코드가 아니라 DB에 있다** → 병원별로 갈아끼우기 가능 |
| 번역기 + 6개 언어 사전 | 한국어 초안 1벌 → 5개 언어 자동 확장 |
| RAG 문서 적재 | 병원 자료(홈페이지·안내문)를 넣으면 AI 상담이 그 병원 지식으로 답함 |
| 크롤·정보 보강 | 병원 기본정보 자동 수집 |

> **판의 절반은 「콘텐츠 공장」이다**: 병원 자료 넣기 → AI가 6개 언어 초안 → 사람이 검수 → 게시.
> 이 흐름이 서면 **병원 1곳 콘텐츠가 몇 주 → 며칠**이 된다. 3단계의 핵심 과제다.

| 5 | **로고가 그림 파일**(SVG) | 글자가 아니라 이미지라 치환이 원천적으로 불가 | ⚠️ **글자 로고로 대체.** 실제 구축에선 **병원 로고 파일을 받아야 한다** |
| 6 | 문의 이메일 하드코딩 | 화면에 직접 박혀 있었음 | ✅ 설정에서 읽게 |
| 7 | 🔴 **병원 이름이 길면 헤더가 깨진다** | 「Иммунная Клиника」가 healwith보다 길어 **러시아어 헤더에서 메뉴와 언어 선택기가 겹쳤다** | ❌ **미해결.** 판에 새길 것: 이름 길이는 설정값이 아니라 **레이아웃 제약**이다 |
| 8 | 🔴 **구조화데이터·법인정보는 치환하면 안 된다** | 법인명·주소·SNS를 이름만 갈면 **기계가 허위 사실로 받는다**(#1122에서 고친 부류) | ✅ 기본 테넌트가 아니면 **아예 안 내보냄**. 병원 실제 정보를 받아 새로 만들어야 함 |

### 이 실험이 로드맵에 준 정정

- **§10-2 「기계가 만들 수 있다 36개」는 유효하다** — 브랜드·문구 쪽은 실제로 설정 하나로 갈렸다.
- **다만 §10-3(콘텐츠)이 예상보다 더 무겁다.** 문구는 갈렸지만 **내용 자체는 여전히 healwith 이야기**다. 면력 화면인데 「원격 사전상담 컨시어지」를 설명하고 있다. **이름 갈아끼우기 ≠ 그 병원 사이트.** 진짜 필요한 건 **병원별 콘텐츠 씨앗**(§10-6 ④).
- **자산(로고·사진)이 새 항목으로 추가된다.** 열쇠 64개 목록에 없던 종류다 — 코드도 설정도 아닌 **파일**이라 병원에서 받아야 한다.

### 남은 목업 작업(하려면)

브랜드는 갈렸으니 다음은 **내용**이다: 면력 4개 지점(강서·신촌·광명·성동)·한방 면역치료 8개 진료영역·센터 단가 54건은 이미 DB에 있다 → 홈 문구·암종 페이지를 면력 것으로 바꾸면 «보여줄 수 있는» 목업이 된다. **PO가 원하면 이어서 한다.**

## 10-6. 중기-B (12월 ~ 2027년 2월) — **판 1차: 설치 마법사**

> 2단계 기록에서 **두 번 이상 반복된 것만** 자동화한다.

| 만들 것 | 내용 | 효과 |
|---|---|---|
| **① 병원 설정 파일 1개** | 지금 코드 여기저기 흩어진 브랜드명·연락처·언어·진료영역·법인정보를 **파일 하나(`tenant.config`)로 모은다** | 브랜드 갈아끼우기: 며칠 → **10분** |
| **② 열쇠 자동 발급 스크립트** | 보안 열쇠 랜덤 생성 + DB(Supabase)·화상(LiveKit) 프로젝트를 **API로 자동 생성** | 36개 수작업 → **명령 1번** |
| **③ 콘텐츠 씨앗(seed) 뭉치** | 기본 문구·페이지·FAQ·법률문서 틀을 **한 벌로 심는다**(병원명만 치환) | 빈 사이트 → 첫날부터 형태 있음 |
| **④ 콘텐츠 공장 1차** | 병원 자료 넣기 → AI 6개 언어 초안 → 검수 화면 | 콘텐츠 몇 주 → **며칠** |
| **⑤ 신청 대행 체크리스트** | WhatsApp·메일 도메인 등 **바깥 승인 28건**을 계약 첫날 동시에 거는 순서표 + 위임장 양식 | 기다리는 시간이 **겹쳐서** 줄어듦 |
| **⑥ 법률문서 생성기** | 개인정보처리방침·약관에 병원 법인명·사업자번호를 꽂아 생성 | 필수 3문서 자동 |

| | |
|---|---|
| **달성 목표** | **병원 1곳 = 3일** (사람이 붙는 건 반나절) |
| **아직 안 하는 것** | 한 시스템에 여러 병원 태우기(멀티테넌트) — 여전히 사본 복제 |
| **왜 아직** | 사본 복제는 **한 곳이 터져도 다른 병원에 안 번진다.** 의료 데이터라 이 격리가 안전하고, 5곳까지는 이게 더 싸다 |
| **다음 단계로 넘어가는 조건** | **운영 중인 병원 5곳** 또는 **사본 관리 비용이 통합 개발비를 넘을 때** |

## 10-7. 장기-A (2027 상반기) — **판 2차: 한 시스템에 여러 병원**

> 5곳을 넘어가면 사본마다 업데이트·서버비·장애 대응이 사람을 잡아먹는다. 그때 합친다.

| 만들 것 | 왜 |
|---|---|
| **테이블마다 「어느 병원 것인지」 칸 추가 + 접근권한 규칙(RLS) 격리** | 지금 대부분 테이블에 이 칸이 없다 = 이 작업이 이 단계의 전부라 해도 됨 |
| **병원별 주소(도메인) 자동 연결** | `병원이름.우리도메인` 또는 병원 자체 도메인을 붙이면 알아서 그 병원 화면 |
| **관리자 화면의 「새 병원 만들기」 버튼** | 3단계의 명령어를 **화면 버튼**으로. PO가 셸을 안 열어도 됨 |
| **업데이트 한 번 = 전 병원 반영** | 사본 시절의 가장 큰 짐이 사라진다 |
| **병원별 성과판 + 청구 자동화** | 유치 건수·상담 수를 병원별로 갈라 보여주고 그대로 청구서로 |

| | |
|---|---|
| **달성 목표** | **병원 1곳 = 반나절** (사람은 승인 30분) |
| **주의** | 🔴 **의료 데이터가 한 곳에 섞인다.** 접근권한 규칙(RLS)이 뚫리면 A병원이 B병원 환자를 본다 = 사업이 끝나는 사고. **이 단계는 반드시 독립 보안 점검을 거친다** |
| **다음 단계 조건** | 병원 10곳 + 문의가 우리 처리 속도를 넘을 때 |

## 10-9. 단계마다 「멈추는 조건」 (제일 중요)

각 단계는 **다음 조건을 못 채우면 다음으로 넘어가지 않는다.** 이걸 안 지키면 고객 없이 공장만 커진다 — 의료관광 플랫폼이 죽는 가장 흔한 방식이다(Medigo: €10.75M 조달하고 폐쇄).

| 단계 | 넘어가려면 |
|---|---|
| 단기 → 중기-A | 8/27 평가 종료 |
| 중기-A → 중기-B | **유료 계약 1건** (또는 레퍼런스 1 + 의향서 1) |
| 중기-B → 장기-A | **운영 병원 5곳** |
| 장기-A → 장기-B | **유료 병원 10곳 + 이탈률 안정** |

## 10-10. 이 로드맵이 KHIDI 과제와 어긋나지 않는 이유

- 중간평가(8/27)까지는 **개발 0** — 실적에 손해 없음.
- 「타 의료기관 확산」은 정부과제가 좋아하는 **성과 확산** 스토리다. 매각은 제약이지만 **사업화는 성과로 인정**된다.
- ⚠️ 단 **협약서의 결과물 사업화 조항 확인은 PO 몫**(서명본 실물이 PO에게만 있음). 최종평가·정산 완료 전에 큰 계약을 맺을 거라면 그 전에 확인이 필요하다.
