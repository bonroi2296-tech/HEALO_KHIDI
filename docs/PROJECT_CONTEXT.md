**2. 왜 그렇게 했는지**
- **유치문서 780MB 중 14건만 git 에 넣은 이유**: 통째로 ignore 하면 이 문서들이 PO PC 한 곳에만 존재 = 하드 고장이면 소실인데, 재다운로드 불가한 것(협약서 원문·법령·매뉴얼·등록서식)만 추리면 **12.9MB** 라 그냥 저장소에 넣으면 영구 자동백업된다 → **PO 가 클라우드 백업을 따로 설정할 일이 없어진다.** 나머지 765MB 는 PDF 6개가 GitHub 100MB/파일 제한을 넘어 push 자체가 불가.
- **「완료」를 자동으로 찍게 고치지 않은 이유**: `app/api/livekit/webhook/route.ts` 가 room_finished 에서 status 를 안 건드리는 건 **의도된 설계**(주석에 명시 — 방이 물리적으로 닫혔다고 상담이 성사된 건 아니므로 사람이 확인 후 누르게 함 = 실적 정직성). 자동화하면 KHIDI 실적이 부풀려진다. 그래서 설계는 그대로 두고 **안 누른 사실을 시끄럽게 만드는 쪽**으로 풀었다.
- **새 cron 을 안 만든 이유**: `dispatch-surveys` 가 이미 같은 테이블을 매일 읽고 인과도 직결(설문이 0인 이유가 바로 completed 가 없어서)이라 그 자리에 얹음.
- **구글 비즈니스를 「방문 서비스 업체」로 권한 이유**: 구글 규정이 *"고정된 현장 간판이 없으면 오프라인 매장으로 간주되지 않으며, 방문 서비스 업체로 등록해야 합니다"* 로 못박혀 있고, 613호 문패는 **`BONROI`** 인데 프로필 이름은 **`healwith`** 라 매장 인증으로는 "이름 불일치" 반려가 확정적. 다만 **먼저 공짜로 시도**하는 게 순서라 결론은 "BONROI 문패 그대로 일단 찍어봐라"로 정정(아래 4번 PO 취향).

**4. 주의·함정** ⚠️ **여기가 이 핸드오프의 핵심**
- 🔥 **어시가 같은 기능(#811)에 결함을 2번 냈고 둘 다 독립 리뷰가 잡았다. 자기 코드 자기 판정은 이 세션에서도 실패했다.**
  - **1차**: 새로 쓴 쿼리의 `error` 를 안 봄. supabase-js 는 PostgREST 오류에 reject 하지 않고 `{data:null, error}` 로 resolve → 컬럼·RLS 가 바뀌면 대상 0건이 되고 응답은 `ok:true` → **"울릴 게 없음"과 "감지가 죽음"이 구별 불가.** 조용한 실패를 막으려고 만든 감지기가 조용히 죽는 구조였다. (같은 파일 위쪽 본 쿼리는 `sessErr` 를 체크하는데 새로 쓴 데만 빠뜨림.)
  - **2차(더 나쁨)**: 1차 지적을 고치면서 도배 방지를 "안 읽은 알림 있으면 재발송 안 함"으로 넣었는데, 리뷰어가 **프로덕션 실데이터**를 뽑아 반박 — 이 서비스 알림은 **96%가 영영 안 읽힌다**(ai_quality_alert 353건 중 339건 미열람, 직원 2명이 각 247·246건 미열람). → 첫 발송 뒤 **영구 침묵**, 제목은 "5건"에 고정. 목적의 정반대. **아이러니하게 원래 어시가 쓴 주석에 정답("N일 1회로 줄일 것")이 적혀 있었는데 그걸 버리고 더 나쁜 걸 골랐다.**
  - 교훈: **"고쳤다"가 새 결함일 수 있다. 리뷰 지적을 반영한 뒤에도 반드시 재검증을 돌려라**(이번엔 3라운드 돌렸고 2·3차에서 각각 건졌다).
- ⚠️ **`consultation_sessions` 를 mock 할 땐 호출 순서로 나눠라** — `dispatch-surveys` 라우트는 이 테이블을 **두 번** 읽는다(1회차 설문 대상 / 2회차 넛지 대상). 한 덩어리로 mock 하면 넛지 쿼리만 실패하는 상황을 재현할 수 없다(설문 쿼리까지 죽어 500 조기반환). 계약 테스트 작성 중 실제로 겪음.
- ⚠️ **`.gitignore` 에서 「전부 제외 후 `!` 로 골라내기」는 조용히 무시된다** — git 이 제외된 폴더 내부를 아예 탐색하지 않아서다(`git check-ignore` 로 확인함). **「무거운 폴더만 명시 제외」로 뒤집어 써야** 한다. 실제로 이번에 한 번 헛돌았다.
- ⚠️ **구글 비즈니스: 「카자흐=얀덱스」와 별개로, 프로필 이름(`healwith`)과 문패(`BONROI`) 불일치가 인증의 관문이다.** 다만 홈페이지 푸터에 `Service Name: healwith / Operated by: Bonroi / Address: Room 613, 385 Gangseo-ro` 가 **이미 다 적혀 있어** 그 한 화면이 둘을 잇는다 → 동영상에서 **문패 찍은 직후 바로 푸터를 보여주는 순서**가 승부처.

## 2. 핵심 전략 결정 (왜)
- **"병원 매칭 마켓플레이스" 아님 → "연속 케어 컨시어지"**: 제휴 병원이 면력한방병원 3곳(진단·면역·재활, 수술 X) + 협진 대학병원 4곳(수술·항암)뿐. 100개 중 1개 고르는 게 아니라 **진단→수술 연계→면역·재활을 쭉 잇는** 모델. 그래서 홈·AI챗·치료여정의 "매칭" 표현을 "케어 경로/상담 배정"으로 톤다운함. (`/care-journey` 페이지가 이 스토리)
- **매칭 엔진 코드는 보존**하되 환자 전면엔 안 붙임 (미래 확장용).
