## 2. 설계 원칙 (먼저 정하고 나서 붙인다)

1. **진실원천을 나눈다.** 「매출 얼마?」 = **카페24**(취소·환불 반영된 실매출). 「어디서 온 사람이 사나?」 = **GA4**.
   이 선을 안 그으면 두 숫자가 다를 때마다 «어느 게 맞냐»로 시간을 버린다.
2. **GA4 숫자는 항상 「주문 기준」이다.** 취소를 반영해도 **취소 시점**에 빠진다(주문한 날로 소급되지 않는다).
   그래서 GA4 안에서 월별 매출을 볼 땐 **「이 달 주문 – 이 달 취소」**가 되어 살짝 어긋난다. 정확한 월매출은 카페24.
3. **키는 주문번호다.** `purchase` 의 `transaction_id` = 카페24 주문번호. **취소를 보낼 때도 같은 주문번호**를 써야
   GA 가 짝을 맞춘다. 이 규칙이 깨지면 취소가 「짝 없는 환불」로 떠서 아무 의미가 없다.
4. **만들지 않을 것도 정한다.** 전자상거래 값(상품명·카테고리·금액·주문번호)은 GA4 **기본 제공**이다 →
   **맞춤 측정기준을 만들면 안 된다**(같은 걸 두 번 세거나 보고서가 지저분해진다). 실제로 프로벨르는 **0개가 정답**.
5. **광고에 값을 보낼 때가 진짜 위험지점.** 취소가 안 빠진 매출로 광고를 최적화하면 **잘 안 팔리는 광고에 예산이 몰린다.**
   지금은 표본이 작아 영향 없지만, 인스타 유료 유입이 이미 잡히고 있어서 **취소율이 커지면 이게 제일 큰 손해다.**

## 3. 취소·환불을 GA4 에 반영하는 3가지 방법

| 방법 | 어떻게 | 드는 것 | 정확도 | PO 손 |
|---|---|---|---|---|
| **A. 안 한다** | GA4 = 주문 기준으로만 읽는다. 실매출은 카페24 | 0 | 취소 미반영 | 없음 |
| **B. 사람이 모아 붓기** | 카페24 취소 목록 **엑셀 내려받기** → 내가 스크립트로 GA4 에 `refund` 전송 | 스크립트 20분 + **월 1회 사람 손** | 정확(월 단위 지연) | 엑셀 1회/월 |
| **C. 반자동(권장)** | 카페24 **관리자 API**(자체 앱)로 취소를 매일 조회 → 서버가 GA4 로 `refund` 전송 | 반나절 개발 + 힐위드 서버의 정기 실행 재사용 | 정확(하루 지연) | **카페24 개발자 앱 승인 1회** |

- **C 를 권장하는 이유**: 「사람이 매달 잊지 않고 하는 절차」는 반드시 언젠가 빠진다. 한 번 만들면 잊어도 돈다.
- **C 에 필요한 것**: ①카페24 개발자센터에서 자체 앱 만들고 권한 승인(**PO 로그인 1회**) ②GA4 스트림의
  **측정 프로토콜 비밀번호** 발급(내가 함) ③정기 실행은 힐위드 서버의 예약 실행 자리 재사용(별도 비용 없음).
- ⚠️ **아직 확인 안 한 것**: 카페24 관리자 API 가 「취소 목록」을 어느 권한으로 주는지, 그리고 **자체 앱이 심사 없이
  바로 되는지**. 조사 전이라 **반나절은 어림값**이다 — 조사에서 막히면 B 로 내려온다.

2. **전자상거래 값에 맞춤 측정기준 만들지 마라** — 기본 제공이다(§2-4).
3. **전환 별표는 「지난 28일 안에 실제 발생한 이벤트」에만 달 수 있다** — 목록에 없으면 이름을 직접 넣을 칸이 없다.

   대행사의 묵은 미게시 변경 9건**이 있으니 거기서 게시하면 그게 같이 나간다.
