# 다국어 DB 콘텐츠 번역 계획

## 1. 현재 상태

| 구분 | 번역 여부 | 비고 |
|------|-----------|------|
| **UI (버튼/메뉴/라벨)** | ✅ 됨 | `src/lib/i18n` DICTIONARY + `t(key, lang)` |
| **DB에서 가져오는 콘텐츠** | ⚠️ 구조만 있음 | 병원명, 시술명, 설명 등은 `i18n` JSONB·`localize()` 있지만 **데이터가 비어 있으면 영어(원문)로 fallback** |

- **DB 스키마**: `hospitals.i18n`, `treatments.i18n` (JSONB) 이미 존재.
- **코드**: `src/lib/language.js`의 `localize()`, `localizeLocation()`, `localizeArray()`로 `record.i18n[lang]` 사용.
- **매퍼**: `mapHospitalRow`, `mapTreatmentRow`가 `lang`을 받아 `localize(h, 'name', lang)` 등 호출.
- **갭**: (1) 화면 언어와 DB 로케일이 한 소스로 안 맞을 수 있음(아래 2절에서 정리). (2) DB에 번역을 **몇 개 언어까지, 어떤 방식으로** 채울지 전략이 없음.

---

## 2. “오바” 피하기 – 권장 원칙

- **20개 언어 전부를 DB에 수동/대량으로 채우는 건 오바**라고 보는 게 맞음. 운영·품질 관리 부담이 큼.
- **권장**: **주요 4개 언어(en, ko, zh, ja)만 DB i18n을 채우고**, 나머지 16개는 **UI만 번역 + 콘텐츠는 영어(또는 en fallback)** 로 두는 단계적 접근.

---

## 3. 전략 옵션 (계획용)

| 옵션 | 내용 | 작업량 | 적합한 경우 |
|------|------|--------|-------------|
| **A. 4개 언어만 DB** | en/ko/zh/ja만 `hospitals.i18n`, `treatments.i18n` 채움. 나머지 언어는 UI만 번역, 콘텐츠는 en fallback | 중간 (번역 데이터 작성·입력) | 지금처럼 “오바 아니게” 가져가고 싶을 때 |
| **B. 런타임 번역 + 캐시** | 요청 시 (entity, lang) 조합으로 번역 API 호출 후 DB 또는 Redis에 캐시. DB에는 안 넣고 캐시만 쌓음 | 초기 구현 중간, 비용·모니터링 필요 | 언어 추가는 쉽게, 비용/품질은 관리 가능할 때 |
| **C. 하이브리드** | 4개는 DB i18n, 그 외는 “있으면 i18n 사용, 없으면 en fallback” 또는 선택적으로 B | A + (B 일부) | 트래픽 많은 4개는 품질 확보, 나머지는 점진 확장 |

**당장 적용 계획에는 A를 기본**으로 두고, 나중에 필요하면 B/C를 검토하는 걸 권장.

## 4. 단계별 계획 (즉시 적용 말고 “할 일” 순서)

### Phase 0: 언어 소스 통일 (선택·빠른 수정)
- **목표**: 헤더에서 고른 언어(healo_lang)와 DB 콘텐츠에 쓰는 `lang`이 같게.
- **방법**: `src/lib/language.js`의 `getCurrentLangCode()`, `getLocationColumn()` 등이 **healo_lang 쿠키**를 사용하도록 변경 (또는 `getLangCodeFromCookie()`를 재사용).
- **효과**: 한국어 선택 시 `location_kr`·기존 한글 필드가 잘 나오고, 러시아어 등은 자동으로 en fallback만 쓰게 됨. 추가 DB 작업 없이도 동작이 일관됨.

### Phase 1: 4개 언어 DB i18n 정의
- **대상 테이블**: `hospitals`, `treatments`.
- **대상 필드**: 노출되는 텍스트 (예: `name`, `description`, `tags`, `specialties`, `location`은 이미 location_kr/location_en 있으면 그대로 활용 가능).
- **i18n 구조**: 기존처럼 `i18n.en`, `i18n.ko`, `i18n.zh`, `i18n.ja` 각각 `{ name, description, tags?, ... }` 형태.
- **작업**:  
  - 스키마/컬럼 추가 없음 (이미 i18n 있음).  
  - 관리자/엑셀/스크립트로 번역 채우기.  
  - 가능하면 “자동 번역 스크립트 → 검수” 파이프라인 한 번 설계 (예: en 기준으로 ko/zh/ja 생성 후 사람이 수정).

### Phase 2: 채우기 우선순위
1. **진료(treatments)**: 카드/리스트에 보이는 `name`, `description`, `tags` 우선.
2. **병원(hospitals)**: `name`, `description`, `tags`, `specialties` 우선.
3. 상세 페이지용 긴 텍스트(`full_description` 등)는 그다음.

### Phase 3: (선택) 그 외 언어
- 4개 외 언어는 **당분간 DB i18n 채우지 않음**.
- 나중에 특정 언어 수요가 생기면:  
  - 수동으로 해당 언어만 i18n 추가하거나,  
  - B/C(런타임 번역+캐시) 검토.

## 5. 작업량 요약 (참고)

| 단계 | 작업 | 예상 규모 |
|------|------|-----------|
| Phase 0 | language.js가 healo_lang 사용하도록 수정 | 소 (파일 1개, 함수 몇 개) |
| Phase 1 | i18n 필드 정의·가이드 (어떤 키에 무엇 넣을지) | 소 |
| Phase 2 | treatments/hospitals 4개 언어 데이터 채우기 | 중~대 (건수·번역 품질에 따라) |
| Phase 3 | 그 외 언어 또는 런타임 번역 | 필요 시 별도 검토 |

## 6. 언어 선택 UI 원칙

- **선택지에 넣는 언어 = UI + 콘텐츠 둘 다 지원하는 언어만** 노출한다.
- 그래서 현재는 **4개(English, 한국어, 中文, 日本語)만** 언어 선택 드롭다운/모바일 메뉴에 노출한다.
- 프랑스어 등 나머지 언어는 “선택은 되는데 콘텐츠는 영어”가 되면 오히려 신뢰를 깎으므로, **DB i18n(또는 동등한 콘텐츠)을 준비한 뒤에** 해당 언어를 선택지에 추가하는 방식으로 확장한다.

## 7. 정리

- **UI는 이미 번역됨**, DB에서 오는 콘텐츠는 **구조(i18n + localize)는 있으나 데이터가 비어 있어서** 영어로 나오는 상태가 맞음.
- **전부 DB화하는 건 오바**이므로, **4개 언어(en/ko/zh/ja)만 DB i18n을 채우는 계획**을 기본으로 두고,  
  먼저 **Phase 0으로 언어 소스만 맞춰 둔 뒤**, Phase 1–2를 순서대로 진행하는 구성이 무난함.
- **선택 가능 언어 = 실제로 UI+콘텐츠 모두 제공하는 4개만** 노출해, “선택했는데 반쪽만 번역”인 상황을 막는다.
