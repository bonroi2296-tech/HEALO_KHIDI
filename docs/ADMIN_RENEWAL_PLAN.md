# 어드민 백오피스 리뉴얼 로드맵 (계층 통합 관제)

> 작성 2026-07-24. PO 질문 "어드민이 모든 계층을 모니터링·관리하게 만들려면 어디서부터?"에 대한 실측 기반 단계별 계획.
> **이 문서 = 리뉴얼 작업의 단일 SoR(single source of truth).** 각 단계를 착수/완료하면 체크박스와 날짜를 갱신할 것.

## 0. 현황 실측 (2026-07-24, 코드 기준)

### PO가 느끼는 문제 3개 = 실제 코드에서 전부 확인됨

| PO 체감 | 코드 실측 근거 |
|---|---|
| ① 어드민 메뉴가 리뉴얼 전·후 섞여 있다 | 메뉴 정의는 `app/admin/_components/AdminNav.jsx` 한 파일(6그룹). 「레거시 도구」 그룹(대량Import·데이터보강·시스템관측·플레이북+하위3)이 옛 디렉토리 시절 잔재로 명시돼 있고, 메뉴에 안 걸린 고아 화면도 있음(`/admin/crawl/review`). |
| ② 코디·에이전시 백오피스 개선을 어드민이 팔로우 못 한다 | 코디는 최근 콘텐츠 편집기(`/coordinator/content`, #918·#932) 등이 붙었지만 어드민 화면 어디에도 "코디가 뭘 바꿨는지" 피드가 없음. `content_change_log` 테이블은 이미 있는데 보는 화면이 없음. |
| ③ 계층 간 데이터 동기화 준비 부족 | 핵심 테이블(inquiries·consultations·referrals)은 공용인데 **접근 계층이 비대칭**: admin API ~60개 vs coordinator 전용 API 4~5개(brief·request-info·assign·opinions), clinic은 전용 API 0개. 코디는 유치전환 클릭이 admin 전용 API라 불가(KNOWN_ISSUES 기록). |

### 계층별 백오피스 성숙도 (라우트 수 · 설명서 갱신일)

| 계층 | 화면 수 | 설명서 updated | 상태 |
|---|---|---|---|
| admin | 40+ | 07-23 | 최다 기능·구조 노후(피벗 전 메뉴 혼재) |
| coordinator | 14 | 07-21 | 최근 개선 활발(CMS 편집기 등) |
| hospital(국내병원) | 4 | 07-15 | 일부 "준비 중" 표기 |
| agency(해외에이전시) | 1 | 07-09 | 정체 |
| clinic(해외의료기관) | 1 | 06-24 | 가장 정체(전용 API 없음) |

**핵심 진단**: "동기화가 안 된다"의 실체는 데이터가 갈라진 게 아니라(테이블은 공용 = 이미 단일 SoR), **①어드민이 다른 계층 활동을 볼 창이 없고 ②계층별 API 권한이 들쭉날쭉**한 것. 따라서 데이터 마이그레이션 같은 큰 공사가 아니라 "보는 창 + 권한 정리"가 본질.

## 단계별 계획 (한 번에 뚝딱 X — 각 단계가 독립적으로 배포 가능)

### 1단계 — 어드민 메뉴 대청소 + 실사용 지도 ⬜
**목표**: 리뉴얼 전·후 혼재 해소. 어드민을 열면 "지금 사업(피벗 후)"만 보이게.

- 메뉴 40+개 각각에 대해 **실데이터 유무를 실측**(각 화면이 읽는 테이블의 최근 행 수·마지막 갱신일) → 산 화면 / 죽은 화면 / 애매 3분류 표 작성.
- 죽은 화면은 **소프트 정리**(코드 보존, 메뉴에서 제거 — `/stories` 방식). 고아 라우트(`/admin/crawl/review`)는 메뉴에 걸거나 같이 정리.
- 메뉴 그룹을 피벗 후 구조로 재편(운영현황/환자여정/제휴자원/AI품질/계정·시스템은 유지, 레거시도구는 실측 결과에 따라 처분).
- 🛑 PO 결정 포인트: "애매" 분류 화면의 처분(버튼으로 물어봄). 삭제는 없음(전부 가역).
- 산출물: 정리된 AdminNav + `docs/ADMIN_RENEWAL_PLAN.md`에 실사용 지도 표.

**왜 첫 번째인가**: 제일 싸고(하루 안팎) 즉시 체감되며, 실사용 지도가 2·3단계의 설계 입력이 된다.

### 2단계 — 계층 관제 허브 (어드민 홈 개편) ⬜
**목표**: PO 페인 ② 직접 해결 — 어드민 대시보드에서 5계층 활동이 한눈에.

- 어드민 홈(`/admin`)에 **계층별 활동 카드**: 코디(오늘 처리 케이스·콘텐츠 편집 이력), 에이전시(신규 의뢰), 병원(리드 응답), 환자(신규 문의·채널별) — 전부 기존 테이블 집계라 새 테이블 불필요.
- **변경 피드**: `content_change_log`(이미 존재) + 감사로그(`/admin/audit`)를 묶은 "최근 계층별 활동 타임라인".
- 산출물: 새 어드민 홈 1화면 + 설명서(`src/lib/manuals/index.js` admin 섹션) 동시 갱신.

### 3단계 — 계층×데이터 권한 정합화 ⬜
**목표**: PO 페인 ③ — 같은 데이터를 계층별로 "권한에 맞는 뷰"로 접근하게 표준화.

- **권한 매트릭스 실측**: 계층(5) × 핵심 데이터(문의·케이스·상담·의뢰·콘텐츠·만족도)로 "읽기/쓰기/없음"을 코드에서 뽑아 표로. 이 표가 이후 모든 신규 기능의 기준이 됨.
- 매트릭스에서 드러난 구멍 수리 — 이미 알려진 것: 코디 유치전환 클릭 불가(admin 전용 API → `requirePortalAuth(staffOnly)` 전환), 코디 목록 API 부재.
- 원칙 고정: **테이블은 공용(단일 SoR), 계층별로 API 게이트만 다르게** — 계층별 사본 테이블 금지(동기화 문제를 애초에 안 만듦).

### 4단계 — 하위 계층(에이전시·해외의료기관·국내병원) 소생 또는 동결 ⬜
**목표**: 정체된 3계층의 방향 결정 후 실행.

- agency(1화면)·clinic(1화면·API 0)·hospital("준비 중" 잔존)은 **실사용자가 있는지가 관건 = PO만 아는 정보** → 계층별로 "키운다/현상유지/접는다"를 버튼으로 확정 후 착수.
- 키우기로 한 계층만: 화면 보강 + 전용 API + 설명서 갱신 + 2단계 허브에 카드 연결.

## 순서의 논리 (요약)

1. **청소 먼저**(1) — 지도 없이 허브를 지으면 죽은 메뉴 위에 새 층을 올리는 꼴.
2. **보는 창**(2) — 가장 아픈 "팔로우 안 됨"을 새 테이블 없이 해결.
3. **권한 정리**(3) — 2에서 카드 만들며 드러나는 권한 구멍을 표준으로 봉합.
4. **하위 계층**(4) — 사업 판단(PO) 필요라 마지막.

각 단계는 독립 PR·독립 배포 — 중간에 멈춰도 그 지점까지는 온전히 동작.
