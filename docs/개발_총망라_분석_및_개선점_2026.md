## 2. UI/UX 개선점

### 2.1 시술 자동생성 플로우
- **현재**: 실패 시 amber 배너 + 건너뛰기 체크 + 다시 시도. 성공 시 모달에서 확정 저장.
- **개선**:
  - 실패 사유가 길 때 **접기/펼치기** 또는 툴팁으로 요약 노출.
  - **진행 단계 표시**: "크롤링 중 → 시술 추출 중 → 완료" 단계별 텍스트/스피너로 체감 대기 시간 완화.
  - **웹사이트 미등록** 시 병원 편집 폼의 웹사이트 필드로 바로 포커스/안내 문구 링크.

### 2.2 Toast
- **현재**: 에러는 자동 닫힘 없음, 닫기 버튼으로 제거.
- **개선**:
  - **여러 Toast** 쌓일 때 최대 개수 제한(예: 3개) 또는 "모두 닫기" 버튼.
  - **접근성**: `role="alert"`, `aria-live="polite"` 등 스크린 리더 대응.
  - **메시지가 객체**일 때 `JSON.stringify` 대신 `message?.message ?? String(message)` 등 안전한 표시.

### 2.3 관리자 공통
- **로딩/에러 상태**: 일부 목록/폼이 로딩·에러 시 스켈레톤/일관된 에러 UI 없음 → **공통 로딩/에러 컴포넌트** 도입 검토.
- **모바일**: 관리자 페이지가 데스크톱 위주 → **반응형·터치 터미널** 점검(테이블 가로 스크롤, 버튼 터치 영역).

## 3. 비즈니스/기능 개선점

### 3.1 시술 자동생성
- **재시도 정책**: 현재는 수동 "다시 시도"만. **일괄 재시도**(건너뛰기 해제 후 N개 병원 순차 Preview) 또는 **스케줄 재시도** 옵션 검토.
- **품질 피드백**: 추출된 시술 3개에 대해 "적합/부적합" 피드백 수집 시, LLM 프롬프트/신뢰도 임계값 개선에 활용 가능.
- **동적 사이트**: SPA 등으로 HTML에 텍스트가 적을 때 현재 fetch 기반 크롤로는 한계 → **Playwright/브라우저 렌더** 옵션(비용·속도 트레이드오프) 문서화 또는 플래그 도입.

### 3.2 병원/시술 데이터
- **웹사이트 검증**: 저장 시 URL 형식·접근 가능성 간단 검증(헤드 요청)으로 잘못된 URL 조기 발견.
- **시술 출처 추적**: `treatment_sources` 이미 있음 → 관리자 UI에서 "이 시술 출처 보기" 링크로 투명성 확보.

## 4. 운영(Operations) 개선점

### 4.1 배포·환경
- **환경 변수 일원화**:
  - `.env.example` / `docs/VERCEL_DEPLOYMENT_CHECKLIST.md`에 **시술 자동생성·RAG 관련 변수** 명시: `GOOGLE_GENERATIVE_AI_API_KEY`, `OPENAI_API_KEY`, `RAG_DISABLED` 등.
  - Vercel 프로젝트(healo-demo) 기준 **필수 env 체크리스트** 한 페이지로 정리(배포 전 확인용).
- **빌드 없이 배포 검증**: `vercel build` 로컬에서 env 비우고 한 번 돌려 보는 스크립트 또는 CI 단계 추가 시, 배포 깨짐 사전 방지.

### 4.2 마이그레이션
- **20260226_offers_auto_fail_log.sql** 가 Supabase에 **실행되었는지** 배포/운영 체크리스트에 포함.
  - 미실행 시 Preview 실패 로그 저장이 500/에러로 이어질 수 있음 → Runbook에 "DB 로그 실패 시 컬럼 확인" 이미 있음, **마이그레이션 적용 순서** 문서화 권장.

### 4.3 런북·점검
- **시술 자동생성 Runbook 추가**:
  - 정상: Preview 200, `offers.length > 0` 또는 `hint`+`message`로 실패 사유 확인.
  - 이상: `[offers/preview] DB 로그 실패` → 마이그레이션 적용 여부 확인; `extractOffersFromText threw` → LLM API 키·할당량·네트워크.
- **배포 직후 URL 목록**에 다음 포함 검토:
  - `GET /api/admin/hospitals` (목록 200)
  - `POST /api/admin/hospitals/[id]/offers/preview` (관리자 인증 후 200)

### 4.4 로깅·관측성
- **구조화 로그**: `console.error("[offers/preview] ...")` 를 JSON 형태(타임스탬프, 레벨, 메시지, hospital_id 등)로 남기면 Vercel Logs·외부 모니터링 연동 시 유리.
- **메트릭**: 시술 Preview 호출 횟수·성공/실패(hint별)·소요 시간 집계 시, 품질·비용 모니터링에 활용 가능.

## 5. 보안·안정성

### 5.1 시술 파이프라인
- **SSRF**: `ssrfSafeFetch`로 이미 차단. 새로 외부 URL을 쓰는 경로 생기면 동일 레이어 사용 권장.
- **크롤 부하**: 병원당 링크 상위 10개·페이지당 2MB 등 제한 있음. **동시 Preview 호출 수** 제한(예: rate limit 또는 큐) 고려 시, 한 관리자가 여러 병원 연속 실행 시 외부 사이트 부하 완화.

### 5.2 Supabase 브라우저 클라이언트
- **빌드 시 더미 클라이언트**: 서버/빌드 환경에서만 사용되며, 클라이언트 번들에는 env가 인라인되므로 **실서비스에서는 반드시 Vercel에 NEXT_PUBLIC_SUPABASE_* 설정 후 배포** 필요. 문서에 명시 권장.

- **스크립트**: `scripts/test-offers-myeonryeok.mts` 로 파이프라인 E2E 검증 가능. CI에서 주기 실행 또는 PR 시 선택 실행 시 회귀 방지.
- **API 테스트**: `/api/admin/hospitals/[id]/offers/preview` 에 대한 단위/통합 테스트(모킹 크롤·LLM) 있으면 변경 시 안전.

### 6.2 에러 메시지
- **사용자 노출**: Preview 실패 시 `message`가 한글로 나오도록 이미 구성됨. **apply 실패** 시에도 사용자에게 보여줄 메시지를 일관되게 (예: "일부 시술 저장에 실패했습니다. 로그를 확인해 주세요.").

### 6.3 타입·스키마
- **Zod**: `HospitalUpdateSchema`에 `offers_auto_*` 이미 반영. 다른 Admin API에서 부분 PATCH 시 동일하게 필드 추가 시 스키마에 반영 권장.
- **DB 코멘트**: `offers_auto_fail_reason` 등 컬럼에 COMMENT 적용됨. 신규 컬럼 추가 시 COMMENT 유지하면 운영·온보딩에 유리.
