# AI 모델 성능 비교 — 의료특화 에이전트 vs 일반 하이엔드 모델

> **목적(KHIDI 중간평가 대응):** "왜 GPT‑4·Claude 같은 거대모델을 안 쓰고 자체 에이전트를 쓰나?"는
> 8/27 중간평가 단골 질문이다. 이 문서는 그 답을 **방법론 + 실측 도구 + 근거표**로 정리한다.
> 단일 진실(SoR): 평가 차원·가중치·임계값은 `src/lib/chat/qualityStandards.ts`.

---

## 1. 한 줄 결론

우리 에이전트의 강점은 **"모델 IQ"가 아니라 "의료 도메인 특화 파이프라인 + 비용효율"**이다.
우리가 가장 중요시하는 두 지표 **환각(가중 40%) + 안전(35%) = 합 75%**에서, 의료특화 파이프라인을 두른
보급형(flash) 모델이 **아무것도 두르지 않은 하이엔드 맨몸**보다 우위다. 반대로 **순수 추론력** 한 축에서는
하이엔드가 앞선다 — 하지만 의료관광 컨시어지 업무의 병목은 추론력이 아니라 **사실 근거(환각 차단)와
의료 안전선 준수**다.

---

## 2. 왜 보급형 + 특화가 거대모델 맨몸을 이기나 (메커니즘)

| 지렛대 | 설명 | 효과 |
|---|---|---|
| **RAG(검색증강)** | 답을 모델 머리에서 짜내지 않고 **우리 DB(등록 병원·시술·문헌)를 펴놓고("오픈북") 인용** | 없는 병원·가격·의사 이름 **지어내기(환각) 차단**. 거대모델 맨몸은 우리 병원을 몰라 환각 위험 |
| **의료 레드라인 프롬프트** | 진단·치료선택권유·약물용량·생존율예후·검사판독·완치보장(한방/면역)을 **명시적으로 금지** | 도메인 특화 안전선. 범용 모델 기본 안전필터는 이 경계를 모름 |
| **0층 정규식 가드(`safetyGuard`)** | LLM 판사 이전에 **확정적 정규식**으로 완치보장·약물용량·예후수치를 기계가 먼저 차단 | 비용 0·100% 재현·절대 안 놓침. 판사가 놓쳐도 경보 보장 |
| **자기채점·회귀테스트** | 라이브 응답을 매번 채점(`judge.ts`) + 매일 회귀배치 → 대시보드 | 품질이 **숫자로 남음**. 거대모델 API 단순 호출엔 없는 운영 가시성 |
| **비용·속도** | flash = 하이엔드 대비 수~수십 배 저렴·빠름 + 일일 상한 가드(`aiGuard`) | 동일 품질을 싸게. 정부지원과제 지속가능성 |

> 핵심: **공정 비교는 "flash+RAG vs 하이엔드 맨몸"이 아니라 "flash+RAG vs 하이엔드+RAG"**다.
> 같은 RAG를 하이엔드에 물리면 종합력은 더 나아질 수 있다(=상한선). 그래서 벤치에 `highend_spec`
> 비교군(`--full`)을 둬서 **"모델을 바꾸면 얼마나 더 좋아지나(헤드룸)"**까지 측정한다.

## 3. 측정 방법 (실측 도구)

스크립트: `scripts/model-benchmark.ts` · 실행: `npm run bench:models`

### 비교군(arms)
| key | 구성 | 의미 |
|---|---|---|
| `our` | flash + 의료특화 프롬프트 + 컨텍스트 | **우리 에이전트** |
| `highend_raw` | 하이엔드(Gemini Pro) + 범용 프롬프트 + 컨텍스트 없음 | **거대모델 맨몸** |
| `highend_spec` (`--full`) | 하이엔드 + 의료특화 프롬프트 + 컨텍스트 | **공정 비교 상한선** |

### 채점 방법 (업계 정석 중 우리 도메인에 맞는 것만)
표준 LLM 벤치(MedQA 등 "정답 맞히기")는 *진단을 일부러 거절하는 안전형 에이전트*엔 안 맞으므로, 우리 도메인 지표를 쓴다.
1. **절대점수(AI 채점관, LLM-as-judge)**: 환각 0.40 / 안전 0.35 / 관련성 0.25 (`qualityStandards.computeOverall`).
   **채점관 기본 = 하이엔드 모델**(flash 자기채점 편향↓, `BENCH_JUDGE_MODEL`로 변경 가능).
2. **0층 규칙 가드(`safetyGuard.scanRedlines`)**: 레드라인 위반은 판사 점수와 무관하게 안전/종합 바닥 강제.
3. **맞대결(pairwise)**: 우리 vs 하이엔드 맨몸 두 답을 **익명(A/B, 위치 교대로 편향↓)**으로 비교 → **우리 승률%**. 절대점수보다 신뢰성↑.
4. **사람 검수 표본(calibration)**: 일부 문항을 골라 우리/하이엔드 답 + AI 판정을 나란히 노출 → 사람이 직접 "AI 채점이 맞나" 점검(자기채점 편향 비판 차단).
+ 무료 한도(429/quota) 자동 1회 재시도.

### 시나리오(약 48개, 6개 언어 ko·en·ru·kz·zh·ja)
단일 SoR = `src/lib/chat/benchmarkScenarios.ts`. 카테고리: 레드라인(완치주장·진단·치료선택·약물·예후·검사판독·사례보장) +
컨시어지 의도(비용·매칭·원격협진·비자·언어) + 환각 유도(미등록 병원/의사/가격) + 응급 안전 + 공감 우선.
`core`(빠른 실행용 대표 문항)·`calibration`(사람 검수용) 플래그로 구분.

### 실행 모드
- **빠른 실행(quick)**: `core` 대표 문항만 — 저비용·1~2분.
- **정밀 실행(full)**: 전체 약 48문항 — 통계적으로 의미 있음·3~5분.
- **+ 상한선**: 위에 `highend_spec`(하이엔드+우리 파이프라인) 비교군 추가.

### 실행 — 방법 ①: 어드민 버튼 (PO 추천, 키 안 만짐)
어드민 **「AI 품질·시스템 › 모델 성능 비교」**(`/admin/khidi/model-benchmark`) → **"빠른 실행 / 정밀 실행 / 정밀+상한선"** 버튼.
프로덕션 GOOGLE 키로 서버에서 직접 돌고, 맞대결 승률 + 절대점수표 + 사람 검수 표본 + 시나리오별 응답이 화면에 바로 뜬다.
(라우트: `POST /api/admin/khidi/run-benchmark?mode=quick|full&full=1`. `requireAdminAuth` 가드.)

### 실행 — 방법 ②: CLI
```bash
GOOGLE_GENERATIVE_AI_API_KEY=... npm run bench:models             # 전체 문항 + 맞대결
GOOGLE_GENERATIVE_AI_API_KEY=... npm run bench:models -- --quick  # 대표 문항만(빠름·저비용)
GOOGLE_GENERATIVE_AI_API_KEY=... npm run bench:models -- --full   # + 하이엔드+특화 상한선
```
코어 로직은 `src/lib/chat/modelBenchmark.ts` 단일 모듈(어드민 라우트·CLI 공용).
환경변수: `BENCH_HIGHEND_MODEL`(기본 `gemini-2.5-pro`) · `BENCH_JUDGE_MODEL`(기본=하이엔드) · `BENCH_OUR_MODEL`(기본 `gemini-flash-latest`).
타사 하이엔드(GPT‑4·Claude)는 별도 SDK(`@ai-sdk/openai` 등)+키 필요 — 기본은 같은 Google 키로 도는 Gemini Pro.

결과: 콘솔 종합표 + `evaluation_results/model-benchmark-<시각>.md`(시나리오별 응답·플래그 상세).

## 4. 결과 읽는 법

| 보는 지표 | 무엇을 말하나 |
|---|---|
| **안전 점수 / 레드라인 위반 건수** | 의료특화의 핵심 가치. `our`가 `highend_raw`보다 위반이 적어야 정상 |
| **환각 점수** | RAG의 효과. 환각유도 시나리오에서 `our`가 "등록 정보에 없음"이라 답하면 고득점, 맨몸이 지어내면 저득점 |
| **종합 점수 / 통과율** | 75% 가중이 안전+환각 → `our`가 강세일 것 |
| **`highend_spec` vs `our` 격차** | 모델 업그레이드의 헤드룸. 격차가 작으면 "flash로 충분"의 정량 근거 |
| **평균 지연(ms)** | 비용/속도 우위 — flash가 하이엔드보다 빠름 |

## 5. 분석 기반 예상(실측 전 가설 — 숫자는 벤치로 확정)

| 지표(가중) | our (특화 flash) | highend_raw (맨몸) | 예상 우위 |
|---|---|---|---|
| 환각/사실성 (40%) | RAG로 등록정보만 인용 | 우리 병원 모름 → 지어냄 | 🟢 our |
| 의료 안전 (35%) | 6언어 레드라인 + 0층 정규식 | 범용 안전필터(도메인 레드라인 모름) | 🟢 our |
| 관련성/컨시어지 (25%) | 문의 전환 목적 고정 | 일반론·잡담으로 샘 | 🟢 our(약간) |
| 순수 추론·뉘앙스 | flash 등급 | 하이엔드 압승 | 🔴 highend |
| 비용·속도 | 싸고 빠름 + 일일상한 | 비싸고 느림 | 🟢 our |

> ⚠️ 위 표는 **아키텍처 근거의 가설**이다. `npm run bench:models`로 실제 점수를 채우면
> KHIDI 평가용 정량 근거가 된다. (이 환경은 API 키가 없어 실행은 키 있는 환경에서.)

## 6. 한계(정직)

1. **자기채점 편향:** 채점관도 LLM. 그래서 채점관을 하이엔드로 올려 완화했지만 완전 제거는 아님.
   더 엄밀히 하려면 사람 라벨링 표본 + LLM 채점 상관 검증 필요.
2. **Gemini Pro = 하이엔드 스탠드인:** GPT‑4·Claude 직접 비교는 별도 SDK·키·비용 필요. 등급은 동급.
3. **RAG 모사:** 벤치의 컨텍스트는 등록정보를 **모사**한 정적 스니펫(라이브 Supabase 미연동 — 키만으로 돌게).
   라이브 RAG 검색 품질(어떤 자료를 얼마나 잘 찾나)은 별도 지표(`npm run verify:rag`, playbook 감사)로 본다.

## 7. 개선 루프(실측 후)
