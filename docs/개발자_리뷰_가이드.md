## 1. 프로젝트 개요

> 💡 **왜 중요한가** — 이 프로젝트가 어떤 문제를 풀고 있는지 모르면 코드 리뷰 방향을 잡기 어렵습니다. 리뷰어가 "이 기능이 왜 이렇게 복잡하지?"라고 느끼는 이유 대부분은 의료 도메인 특수성 때문입니다.

**TL;DR**: 암환자를 위한 한국 의료관광 AI 컨시어지. 카자흐스탄·러시아 환자가 한국 병원을 탐색하고, AI 상담 후, 화상진료까지 원스톱으로 진행하는 플랫폼.

### 서비스 한 줄 정의

> "카자흐스탄/러시아의 암환자가 한국 최적 병원을 AI로 매칭받고, 언어 장벽 없이 화상 진료까지 받을 수 있는 KHIDI(한국보건산업진흥원) 의료관광 컨시어지"

### 타겟 사용자 (3종류)

| 사용자 | 역할 | 주요 목적 |
|--------|------|----------|
| **환자** (B2C) | 카자흐스탄·러시아 암환자 | 병원 검색 → AI 상담 → 화상진료 → 비자 안내 |
| **파트너 병원** (B2B) | 한국 의료기관 담당자 | 리드 수신 → 환자 오퍼 관리 |
| **내부 팀** | 코디네이터·어드민 | 인테이크 검토 → 병원 매칭 → 모니터링 |

### 핵심 기능 6가지

1. **AI 채팅 상담** — Gemini 2.5 Flash 기반, 암 유형별 병원 추천 + RAG 검색
2. **화상 진료(WebRTC)** — LiveKit 기반 실시간 의사-환자 연결 + 동시 통역
3. **병원/시술 탐색** — KHIDI 인증 병원 DB, 다국어(6개 언어)
4. **인테이크 폼** — 암 유형/병기/치료 이력 수집 → 리드 품질 자동 스코어링
5. **비자 안내** — 의료비자 요건 자동 안내
6. **어드민 대시보드** — 병원 관리, 플레이북, 크롤링, RAG 문서 관리

### 사업 배경

- KHIDI(한국보건산업진흥원) 의료관광 ICT 사업 일환
- 1차 타겟 시장: 카자흐스탄·러시아 (2026년 현재 가장 한국 의료관광 수요 높음)
- 암환자 특화: 일반 의료관광과 달리 고관여·고비용·장기 여정

## 3. 아키텍처 개요

> 💡 **왜 중요한가** — "어떻게 만들어졌는지" 전체 그림이 없으면 리뷰어가 파일 하나씩 보다가 맥락을 놓칩니다. 아키텍처 이해가 있어야 "이 쿼리가 N+1 문제를 일으키는지", "이 컴포넌트가 서버에서 렌더링되는지"를 즉시 판단할 수 있습니다.

**TL;DR**: Next.js App Router 풀스택. 프론트/백이 같은 레포에 있고, `/app/api`가 백엔드 역할. Supabase가 DB+Auth+Storage를 담당. 모든 AI 로직은 서버 사이드에서만 실행.

### 전체 구조도

```
브라우저 (React 클라이언트 컴포넌트)
    │  HTTP/JSON
    ▼
Next.js App Router (/app/api/*)        ← 백엔드 역할
    │  Supabase JS Client
    ├──► Supabase PostgreSQL            ← DB + Auth + Storage
    │      └─ pgvector (RAG 벡터 검색)
    │
    ├──► Google Gemini 2.5 Flash        ← AI 채팅 + 번역
    ├──► LiveKit                        ← WebRTC 화상진료
    └──► AWS SES                        ← 이메일 발송
```

| **화상** | LiveKit | WebRTC SFU, 다자 통화 + 녹화 지원 |
| **배포** | Vercel (서버리스) | 인천 리전으로 한국/아시아 사용자 응답 최적화 |

### 데이터 흐름 예시: 환자 AI 채팅

```
1. 환자 메시지 입력 (브라우저)
    │
2. POST /api/public/chat/message
    │
3. Rate Limit 체크 (IP 기반 인메모리)
    │
4. Supabase → chat_threads, messages 저장
    │
5. RAG 검색: rag_chunks 벡터 유사도 검색
    │
6. Gemini 2.5 Flash 호출 (+ RAG 컨텍스트 + 웹 검색)
    │
7. 스트리밍 응답 → 브라우저
    │
8. 응답 저장 + playbook_patterns 후보 추가
```

## 5. 보안 적용 현황

> 💡 **왜 중요한가** — 이 서비스는 암환자의 진단명, 치료 이력, 재정 정보를 다룹니다. 보안 취약점은 법적 책임(개인정보보호법, 의료법)으로 직결됩니다. 리뷰어가 가장 집중해야 할 영역입니다.

**TL;DR**: 기본 보안 레이어는 갖춰져 있음. 하지만 CSRF, 로그인 Rate Limit, TypeScript strict mode 등 구멍이 있음. 의료 데이터 특성상 프로덕션 전 보강 필요.

### ✅ 적용된 보안 장치

#### 1. 인증 & 인가

**미들웨어 라우트 보호** (`middleware.ts`)
```
/admin/*    → 어드민 역할 확인 (3중 체크)
/partner/*  → 세션 + 병원 사용자 확인
/patient/*  → 세션 존재 확인
/coordinator/* → 세션 존재 확인
```

**어드민 3중 확인 구조**:
1. `user.user_metadata.role === "admin"`
2. `user.app_metadata.role === "admin"`
3. `ADMIN_EMAIL_ALLOWLIST` 환경변수 이메일 목록

**인증 방식**: Supabase Auth (이메일/패스워드 + Google OAuth)  
**세션 저장**: HTTP-only 쿠키 (localStorage 아님 → XSS 탈취 방어)

---

#### 2. Rate Limiting (`/src/lib/rateLimit.ts`)

- **방식**: IP 기반 인메모리 카운터
- **적용 엔드포인트**: `/api/chat` 등 남용 가능성 있는 API
- **정리 주기**: 5분 TTL, 1분마다 자동 cleanup
- **응답**: 429 + `Retry-After` 헤더

---

#### 3. 입력 검증 (Zod)

`/src/lib/validation/admin.ts` 기준:
- `HospitalCreateSchema`: 이름, URL 형식, 위경도 범위, 배열 타입 등
- `HospitalUpdateSchema`: Partial 업데이트
- 모든 UUID, 이메일, 숫자 범위 검증

---

#### 4. 암호화 (`/src/lib/security/encryptionV2.ts`)

- **알고리즘**: AES-256-GCM
- **IV**: 12바이트 (GCM 표준)
- **인증 태그**: 16바이트
- **키 관리**: 버전별 관리 (`v1`), 키 교체(rotation) 설계됨
- **원칙**: Fail-closed (검증 실패 시 에러 throw)
- **보호**: `server-only` 임포트로 클라이언트 노출 차단

---

#### 5. HTTP 보안 헤더 (`next.config.js`)

| 헤더 | 값 | 효과 |
|------|-----|------|
| `X-Frame-Options` | `DENY` | 클릭재킹 방지 |
| `X-Content-Type-Options` | `nosniff` | MIME 스니핑 방지 |
| `X-XSS-Protection` | `1; mode=block` | 구형 브라우저 XSS |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | 참조자 정보 제한 |
| `Strict-Transport-Security` | `max-age=63072000` | HTTPS 강제 (2년) |
| `Permissions-Policy` | 카메라/마이크 기본 거부 | `/consultation/*`만 허용 |
| `Content-Security-Policy` | `default-src 'self'` | 외부 리소스 화이트리스트 제어 |

---

#### 6. Supabase RLS (Row Level Security)

| 테이블 | 정책 |
|--------|------|
| `inquiries` | 공개 INSERT만, 서비스 롤이 READ/WRITE |
| `normalized_inquiries` | 서비스 롤 전용 |
| `hospitals` | 공개 READ |
| `consultation_sessions` | 역할 기반 (환자/의사/어드민) |
| `playbook_patterns` | 서비스 롤 전용 |
| `chat_threads` | 참여자 본인 + 어드민만 |

---

#### 7. 감사 로그 (`admin_audit_logs` 테이블)

모든 어드민 데이터 변경 시:
- 사용자 ID, 액션, 리소스 타입, 변경 전/후 값, 타임스탬프 기록
- 무단 접근 시도도 로깅

### ⚠️ 미흡한 부분 (리뷰 필수)

| 항목 | 현재 상태 | 위험도 | 권장 조치 |
|------|----------|--------|----------|
| **CSRF 보호** | 미구현 | 🔴 높음 | SameSite=Strict 쿠키 + CSRF 토큰 |
| **로그인 엔드포인트 Rate Limit** | 미적용 | 🔴 높음 | Brute-force 공격 가능 |
| **CORS 명시적 설정** | 브라우저 기본값 의존 | 🟡 중간 | 허용 오리진 명시적 정의 |
| **Subresource Integrity (SRI)** | 미적용 | 🟡 중간 | CDN 스크립트 무결성 검증 없음 |
| **TypeScript strict mode** | `false` (비활성) | 🟡 중간 | 의료 데이터 타입 오류 런타임 발견 위험 |
| **Rate Limiting 분산 환경** | 인메모리 (단일 인스턴스만) | 🟡 중간 | 서버리스 멀티 인스턴스 환경에서 우회 가능 |
| **내부 API 서명** | `INTERNAL_*_SECRET` 정의됨, 사용 불명확 | 🟡 중간 | 내부 API 호출 검증 필요 |
| **DB 저장 암호화 확인** | Supabase 설정 의존 | 🟡 중간 | Supabase 대시보드에서 확인 필요 |

## 6. DB 스키마 요약

> 💡 **왜 중요한가** — DB 설계는 서비스의 뼈대입니다. 테이블 구조가 잘못되면 나중에 고치기 매우 어렵고 데이터 손실 위험이 있습니다. 리뷰어가 "이 관계가 맞나?", "인덱스가 있나?", "RLS가 맞게 걸렸나?"를 확인해야 합니다.

**TL;DR**: 20+ 테이블, 65개 마이그레이션. 핵심은 환자 인테이크 → 병원 리드 → 화상진료 세션 흐름. pgvector로 RAG 벡터 검색.

## 9. 개발자 리뷰 포인트

> 💡 **왜 중요한가** — 코드 리뷰 시간은 한정적입니다. 어디를 집중적으로 봐야 하는지 방향이 없으면 표면적인 리뷰에 그칩니다. 이 섹션은 "이 영역을 왜, 어떻게 봐야 하는지"를 안내합니다.

**TL;DR**: 의료 서비스 특성상 인증·데이터 타입 안전성·에러 핸들링이 최우선. Rate Limit과 i18n 구조도 개선 여지 있음.

### 🔴 최우선 (프로덕션 전 필수 확인)

#### 1. 인증 & 인가 플로우

**왜 봐야 하는가**: 인증 누락이 2번 반복 발생(2026-04-08, 04-10). 아직 보호 안 된 라우트가 더 있을 수 있음.

| 확인 항목 | 파일 | 세부 사항 |
|----------|------|----------|
| 미들웨어 라우트 커버리지 | `middleware.ts` | 모든 보호 대상 경로가 포함됐는지 전수 확인 |
| 어드민 3중 체크 로직 | `src/lib/auth/checkAdminAuth.ts` | 로직 순서, edge case 처리 |
| OAuth 콜백 보안 | `app/auth/callback/route.ts` | CSRF state 파라미터 검증 |
| API 라우트 인증 | `app/api/*/route.ts` 전체 | `withErrorHandler`에 인증 포함됐는지 |
| 세션 만료 처리 | 미들웨어 + 클라이언트 | 만료 시 적절한 리다이렉트 |

---

#### 2. 타입 안전성

**왜 봐야 하는가**: TypeScript `strict: false` + `any` 147건. 의료 데이터(암 병기, 약물 이름)가 잘못된 타입으로 저장되면 임상적 위험이 될 수 있음.

| 확인 항목 | 파일 | 세부 사항 |
|----------|------|----------|
| `tsconfig.json` strict 설정 | `tsconfig.json` | `strict: false` → 단계적 활성화 방안 |
| 빌드 에러 무시 설정 | `next.config.js` | `ignoreBuildErrors: true` 제거 가능한지 |
| 의료 도메인 핵심 타입 | `src/lib/cancer/`, `src/lib/consultation/` | `any` 사용 부분 타입 강화 |
| Supabase 자동 타입 생성 | — | `supabase gen types` 실행 여부 (현재 미생성) |
| API 응답 타입 | `app/api/*/route.ts` | 반환 타입 명시 여부 |

---

#### 3. DB 쿼리 효율

**왜 봐야 하는가**: 서버리스 환경에서 N+1 쿼리는 응답 지연과 Supabase 쿼리 비용 급증으로 직결됨.

| 확인 항목 | 파일 | 세부 사항 |
|----------|------|----------|
| N+1 패턴 | `app/api/admin/*/route.ts` | 루프 안에서 개별 Supabase 쿼리 호출 |
| RLS vs 서비스 롤 혼용 | `src/lib/supabase/server.ts` | 어디서 RLS 우회하는지 명확한지 |
| 인덱스 커버리지 | `migrations/` | 자주 조회되는 컬럼에 인덱스 있는지 |
| 페이지네이션 | admin 목록 API | max 200 하드코딩 → cursor 기반 페이지네이션 검토 |
| 트랜잭션 사용 | 리드 배정, 세션 생성 로직 | 원자성 보장 여부 |

**왜 봐야 하는가**: 일관되지 않은 에러 처리는 디버깅 시간을 늘리고, 프론트엔드에 민감한 내부 정보가 노출될 수 있음.

**왜 봐야 하는가**: 10일 간격으로 동일 영역에서 2번 버그 발생. 구조적 문제가 있음. 타겟 시장(카자흐스탄·러시아)이 한국어를 못 하므로 번역 오류는 사용자 경험에 직결.

| DB 콘텐츠 번역 | JSONB `i18n` 컬럼 | 실제 번역 데이터 완성도 |
