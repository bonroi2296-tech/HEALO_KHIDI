- **Production: 「머지는 자유, 배포만 하루 한 번」 (2026-07-28 PO 결정).**
  **PR 은 평소대로 바로 머지해라.** main 에 머지돼도 **실서비스 빌드가 돌지 않는다.**
  하루 한 번 **KST 오후 3시**에 창구가 열리고 **그 한 건만** 빌드된다 — 그날 머지된 것
  전부가 그 한 건에 들어간다.

  **창구를 여는 건 `Vercel 예약`이다** (`app/api/cron/daily-deploy/route.ts`, `vercel.json` 의 `crons`).
  main 의 최신 커밋을 읽어 **Vercel API 로 프로덕션 배포를 직접 만든다**(`target: "production"` +
  `build.env.DEPLOY_WINDOW=1`). 직전 프로덕션 배포와 커밋이 같으면 「새 머지 없음」으로 건너뛴다.

  > ⚠️ **`production` 브랜치는 이제 창구가 갱신하지 않는다 (2026-07-31 이후).**
  > 옛 방식은 깃허브 워크플로가 main 을 그 브랜치로 미는 것이었는데, **깃허브가 예약을
  > 2~3시간 늦게 깨워서**(3일 연속 실측: 오후 3시 예약이 5시 36~48분에 시작) 정시 창구를
  > Vercel 로 옮겼다. 새 경로는 열쇠가 없어 브랜치를 못 민다.
  > → **배포 여부를 `production` 브랜치로 판정하지 마라.** 그 브랜치는 낡은 커밋에 멈춰 있다.
  > 판정은 `/api/health` 의 실서비스 커밋이나 Vercel 배포 목록으로 해라.
  > (깃허브 `Daily Deploy` 워크플로는 **예비**로 남겨 뒀다 — Vercel 경로가 실패해도 늦게라도 나간다.)
  - 급한 것(**장애·보안·PO가 지금 보자고 한 것**)은 기다리지 마라:
    ```bash
    git commit --allow-empty -m "chore: 긴급 배포 [deploy]" && git push
    ```
    또는 `gh workflow run "Daily Deploy (배포 창구)"`
  - ⚠️ **머지했다 ≠ 실서비스에 나갔다.** 「배포됐다」고 말하기 전에 3시 창구가 돌았는지,
    또는 `[deploy]` 커밋이 실제로 빌드됐는지 확인해라.
  - (폐기: `merge-queued` 라벨 + `Batch Merge` 워크플로 — 같은 날 되돌렸다. 라벨은 무시해도 된다.)
- **Preview: 기본 OFF (2026-07-28 PO 승인).** 다른 브랜치를 푸시해도 프리뷰를 안 짓는다.
  프리뷰 링크가 필요하면 **커밋 제목에 `[preview]`** 를 달아라 (빈 커밋도 됨):
  ```bash
  git commit --allow-empty -m "chore: 프리뷰 [preview]" && git push
  ```
  왜: 청구 실측(7/23~7/28) 결과 Vercel 요금의 **94%가 빌드 CPU 시간**이었고, 그중 67%가
  아무도 안 보는 프리뷰였다(5.5일 537배포). 판정 로직 = `scripts/vercel-ignore-build.sh`.
- ⭐ **화면 확인의 기본은 프리뷰가 아니라 「로컬 + 화면 사진」이다 (2026-07-31 PO 지시).**
  로컬 dev 서버를 띄우고 브라우저 도구로 열어 사진을 찍어 대화에 붙여라. **로그인해야 보이는
  화면(코디·관리자)도 로컬에서 된다** — 로그인 폼을 실제로 채워 코디 대시보드까지 여는 것을
  2026-07-31 실측으로 확인했다(예전 「SSR 쿠키 때문에 로컬 로그인 자동화 불가」 기록은 폐기).
  프리뷰가 정말 필요한 경우는 둘뿐이다:
  **① PO 가 자기 폰으로 직접 만져봐야 할 때 ② 외부(병원·에이전시)에 링크로 보여줘야 할 때.**
- 🛑 **Preview 는 기본 「완전 차단」이다 (2026-07-31 PO 지시: 「프리뷰도 내가 필요하면 요청할테니깐
  그건 막아버려」).** `[preview]` 를 달아도 안 지어진다. **어시가 판단해서 여는 통로가 아니다.**
  - **PO 가 요청했을 때만** 여는 절차: Vercel 프로젝트 환경변수 `PREVIEW_DAILY_LIMIT` 을 `1` 로
    올린다 → `[preview]` 커밋을 올려 프리뷰를 짓는다 → **주소를 PO 에게 준 뒤 곧바로 `0` 으로
    되돌린다.** 되돌리는 것까지가 한 세트다.
  - 왜: 창구 도입으로 실서비스 배포는 하루 1건으로 잡혔는데 프리뷰는 안 잡혔다 —
    최근 3일 실제 빌드 50건 중 **프리뷰가 27건(하루 9건)**, 한 작업본에서 5건 연달아 나간 날도
    있었다. 그중 PO 가 실제로 연 건 마지막 한두 개다.
- OS: Windows 11 / Shell: **PowerShell 이 기본**, bash(Unix syntax)도 사용 가능 — 둘은 문법이 다르니 섞지 말 것
  (2026-07-27 정정: 예전엔 "Shell: bash"만 적혀 있어 실제 환경과 어긋났다. 검사기 정규식이 CRLF 에서만
   오작동하던 것도 이 차이에서 나왔다 — 윈도우에서만 빨간불이 뜨면 줄바꿈부터 의심할 것.)

## 절약·정책 장치를 설계할 때 — 아끼는 대상을 잘못 고르면 뒤집힌다

> 2026-07-28 취향 원장에서 이관. 원문 경위는 `docs/PO_PREFERENCES.md` 「보관」.

**비용·정책을 이유로 PO 의 작업 흐름을 막는 설계를 하지 마라.** 빌드비를 줄이려고 「합치기 신청서(PR)에 라벨만 달고 오후 3시까지 대기」로 만들었더니 PO 가 **"머지는 문제 없고 배포가 문제 아냐? 머지는 해도 된다 한거 아님?"** 으로 뒤집었다. 이유는 **PR 을 24시간 붙잡으면 작업이 서랍에 갇힌다**는 것. → 절약·정책 장치를 설계할 때 **「PO 가 실제로 겪는 흐름 중 무엇이 느려지는가」를 먼저 적어보고**, 느려지는 게 작업 진행 자체라면 다른 지점을 조여라(여기선 머지가 아니라 배포였다).

> 2026-07-29 취향 원장에서 이관. 원문 경위는 `docs/PO_PREFERENCES.md` 「보관」.
> *(2026-08-30 회수: origin/work/app-install-link 작업본에만 있던 절을 옮겨 심음)*

**에이전시·환자·인쇄물·QR 처럼 한 번 나가면 회수가 어려운 것은, 내용이 바뀔 것을 전제로 「간접층 한 장」을 먼저 만든다.**

스토어 등록 전이라 「홈 화면에 추가」로 안내해야 하는 상황에서 PO 가 *"정식으로 등록되면 앱스토어로 연결해줘야 하는 거 아님?"* 이라 되물었다. 안내 문구를 6개 언어 자료에 박아 뿌리면 **등록되는 날 그 자료를 전부 회수해서 고쳐야 한다.**

→ 실제 적용: **주소는 `healwith.co.kr/app` 하나만 뿌리고**, 그 페이지가 기기와 등록 상태를 보고 보낸다(안드로이드→Play / 아이폰→App Store / 스토어 주소가 비어 있으면 홈 화면 추가 안내 / PC 는 폰에서 열라는 안내). **전환 스위치는 환경변수 `NEXT_PUBLIC_PLAY_STORE_URL`·`NEXT_PUBLIC_APP_STORE_URL` 두 줄**이고, 둘은 따로 동작해 한쪽만 먼저 등록돼도 다른 쪽이 안 깨진다. 코드(`src/lib/appInstall.ts`)·자료 어느 쪽도 그날 안 건드린다.

## 「된겨?」에는 끝단 실측으로 답하라

> 2026-07-28 취향 원장에서 이관. ※ `CLAUDE.md` 「실측·재검증이 기본값」의 배포판 사례다.

설정을 저장하자마자 PO 가 *"된겨?"* 라고 물었다. 화면에 「저장됨」 토스트가 떠 있어도 그걸로 답하지 말고 ①서버 API 로 설정값 재조회 ②창구를 실제로 실행 ③실서비스 배포가 READY 되는지 ④사이트 HTTP 200 까지 확인해 표로 내라. **PO 의 확인 질문은 「화면이 그렇게 보이나」가 아니라 「진짜 되나」다** — 중간 신호(초록불·토스트·워크플로 success)로 답하면 그게 나중에 거짓말이 된다. (실제로 워크플로가 `success` 인데 배포가 안 나간 경우가 있었다.)
