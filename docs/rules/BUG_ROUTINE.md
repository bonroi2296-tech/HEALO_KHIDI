## ⚠️ 상시 루틴 — 오류는 기계가 잡는다 (PO가 화면에서 찾게 두지 말 것)

**왜:** 옛 모델 콘텐츠 잔재(옛 브랜드·이메일·일부 언어만 적힌 목록 등)를 PO가 스크린샷으로 하나씩 찾는 일이 반복됨. → 사람이 아니라 **자동 검사로 매번 차단**.

- **콘텐츠/브랜드 변경 시**: `npm run check:content` 통과 확인 (CI 매 PR 자동). 옛 브랜드/이메일 잔재·i18n 활성6 언어(ko·en·ru·kz·zh·ja) 키 누락이면 빌드 실패.
- **버그·누락 발견 시 (반응형 금지, 아래 4단계 필수)**:
  1. **반성문**: `docs/POSTMORTEMS.md`에 1건 기록 — 무슨 일 / 왜 못 잡았나(근본원인) / 어떻게 고쳤나 / 재발 방지. **쓰기 전에 과거 반성문에서 같은 부류를 먼저 검색**(grep 키워드) — 재발이면 제목에 **「🔁 #NN 부류 재발」**을 달고, 그때의 방지책이 왜 못 막았는지 1줄 + 그 가드의 보강까지 포함하라(재발률 = 기억 시스템 성적표, 2026-07-05 PO 승인).
  2. **유사 이슈 추가 스캔**: 같은 부류가 다른 데 더 없는지 전수 확인.
  3. **가드 룰 추가**: 가능하면 `scripts/check-content-consistency.mjs`에 **새 검사 룰을 추가**해 그 부류를 영구 차단.
  4. **보고**: 근본원인+방지책을 PO에게 보고.
- 새 i18n 검사 기준: 활성 언어는 **6개(ko·en·ru·kz·zh·ja)**. 언어 목록·"지원 언어" 류 카피는 항상 6개 다 포함(특히 핵심 타겟 **러시아어·카자흐어** 누락 주의).
- **주 1회 문서 건강검진(`/doc-health`, 2026-07-05 PO 승인)**: 살아있는 문서(핸드오프·KNOWN_ISSUES·취향·관문 등)끼리의 모순, 코드 현실과 어긋난 항목(#63 문서-현실 드리프트 부류), 죽은 파일 참조를 스캔해 교정. 세션 시작 훅이 마지막 검진 7일 경과 시 리마인드하며, 기록은 `docs/audit/DOC_HEALTH_LOG.md`. **낡은 문서 = 낡은 기억을 믿고 일하는 사고의 씨앗**이라 사람이 아니라 루틴이 잡는다.

## 사용자 제보는 「증상」이지 「진단」이 아니다

> 2026-07-28 취향 원장에서 이관. 원문 경위는 `docs/PO_PREFERENCES.md` 「보관」.

**데이터부터 전수 대조하고 말하라.** 코디(아셀)가 「저장이 안 됐다」고 한 것이 두 번 모두 **유실 0건**이었다(한 번은 값이 어긋나게 저장됨, 한 번은 화면에 안 보임). 제보 문구를 그대로 믿고 「저장 실패」를 캐면 엉뚱한 걸 고친다.

→ **①기록 ↔ 저장소 전수 대조 ②실서비스 화면 확인 ③그래도 안 맞으면 재현** 순서로 가라. PO 가 원하는 답은 「뭐가 사라졌느냐」가 아니라 **「사라졌는지 아닌지」의 확정**이다.

## 문제를 보고할 때는 재현 화면 + 숫자를 같이 내라

> 2026-07-28 취향 원장에서 이관. ※ 말투 훅에도 축약본이 들어간다.

**「말로만 하지 말고 보여달라」** — PO 가 *"저장바 스티키 문제가 뭔데 말로만 하지 말고 좀 보여달라고"* 라고 직접 요구했다. 글로 「스티키가 안 듣는다」고 설명한 것을 PO 는 몸으로 못 느낀다. → **증상을 실서비스에서 그대로 재현해 스크린샷 + 실측값**(「문서 10,985px 중 버튼은 10,889px 지점」)을 보여줘라. 원인 설명은 그 다음이다.

## 경보·알림 설계를 「메일로 갑니다」로 끝내지 마라

PO 는 메일을 상시 보지 않는다. 2026-07-28 업타임 감시를 붙였을 때 PO 질문:
