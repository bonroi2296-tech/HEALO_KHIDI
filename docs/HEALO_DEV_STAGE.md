# HEALO 개발 단계 정의 문서

**작성일**: 2026-02-04  
**버전**: 1.0  
**상태**: 공식 인수인계 문서

---

## 1. 문서 목적

이 문서는 HEALO 프로젝트의 현재 개발 단계와 구현 범위를 명확히 정의한다.

**방지 대상**:
- "병원 대시보드는 왜 없나요?" 질문 반복
- "리드 자동 배분 기능 구현해야 하지 않나요?" 논의 반복
- hospital_leads 테이블이 존재하므로 "병원 참여형 시스템"으로 오인하는 상황
- 현재 단계에 맞지 않는 기능 제안 및 과도한 자동화 시도

**사용 대상**:
- 새로운 세션을 시작하는 AI 에이전트
- 인수인계받는 개발자
- 프로젝트 현황 파악이 필요한 운영팀

---

## 2. 현재 HEALO 개발 단계 정의

### 현재 단계: **운영자 주도 수동 매칭형 MVP**

**정의**:
- 사용자(환자)가 웹사이트에서 문의를 제출한다.
- 운영자가 Admin 대시보드에서 문의를 확인한다.
- 운영자가 수동으로 적합한 병원을 선택하고 연락한다.
- 병원은 이메일/전화로 응답하며, 플랫폼에 직접 접속하지 않는다.

### 명확히 아닌 것들

| 현재 아닌 것 | 이유 |
|------------|------|
| 병원 참여형 플랫폼 | 병원 계정/로그인 시스템 없음 |
| 병원 SaaS | 병원이 사용하는 대시보드/도구 없음 |
| 자동 리드 분배 시스템 | 분배 로직, 알림 시스템 미구현 |
| B2B2C 마켓플레이스 | 병원-플랫폼 간 양방향 통신 없음 |
| 병원-환자 직접 매칭 | 모든 매칭은 운영자가 수동 처리 |

---

## 3. 현재 사용 중인 핵심 구조

### 데이터 흐름

```
사용자 제출 → inquiries (원본) 
            → normalized_inquiries (정규화)
            → 운영자가 Admin UI에서 수동 확인
            → 운영자가 직접 병원 연락 (플랫폼 외부)
```

### 핵심 테이블

| 테이블 | 역할 | 현재 사용 여부 |
|--------|------|---------------|
| `inquiries` | 사용자 문의 원본 저장 | ✅ 사용 중 |
| `normalized_inquiries` | 정규화된 문의 데이터 | ✅ 사용 중 |
| `hospitals` | 병원 기본 정보 (Admin 관리) | ✅ 사용 중 |
| `treatments` | 시술 정보 (Admin 관리) | ✅ 사용 중 |
| `human_touchpoints` | 운영자 수동 개입 기록 | ✅ 사용 중 |

### 운영자 중심 처리 구조

- **Admin UI**: `/app/admin/*`
  - 문의 조회: `/app/admin/inquiries`
  - 병원 관리: `/app/admin/hospitals`
  - 시술 관리: `/app/admin/treatments`
  - 분석: `/app/admin/analytics`
- **human_touchpoints의 역할**: 운영자의 모든 수동 개입(전화, 이메일, 메모)을 기록하는 테이블. 현재 핵심 운영 데이터.

---

## 4. 존재하지만 '미구현/동결' 상태인 요소

### 4.1. 병원 계정 시스템

**상태**: 미구현  
**사유**: 병원은 현재 플랫폼 사용자가 아님. 운영자가 대신 연락.

| 요소 | 설계 여부 | 구현 여부 | 비고 |
|------|----------|----------|------|
| 병원 계정/로그인 | ❌ | ❌ | 설계 없음 |
| 병원 대시보드 | ❌ | ❌ | 설계 없음 |
| 병원 알림 시스템 | ❌ | ❌ | 설계 없음 |

### 4.2. hospital_leads 테이블

**상태**: 설계 존재, 코드 존재, DB 마이그레이션 준비됨, **현재 사용하지 않음**

**테이블 위치**: `migrations/20260204_hospital_leads.sql`  
**API 위치**: `/app/api/admin/leads/*`  
**UI 위치**: `/app/admin/leads/page.jsx` (메뉴: "리드관리(현재 미구현)")

**설계된 용도**:
- 운영자가 문의(inquiry)를 특정 병원에 할당
- 병원별 응답 상태 추적 (queued, sent, viewed, replied, converted, rejected, expired)
- 병원별 견적가 기록

**현재 사용하지 않는 이유**:
1. 병원 수가 적어 운영자가 수동으로 충분히 관리 가능
2. 문의량이 적어 추적 시스템이 불필요
3. 병원이 플랫폼에 접속하지 않으므로 'viewed' 상태 등이 무의미
4. 운영자가 전화/이메일로 처리하며 human_touchpoints에 기록하는 것이 더 자연스러움

**동결 상태 유지 조건**:
- 현재 월 문의 50건 미만
- 연락하는 병원 수 10곳 미만
- 운영자 1-2명으로 처리 가능

### 4.3. 병원 응답 추적 (hospital_responses)

**상태**: 설계 존재, 현재 사용하지 않음

**이유**: hospital_leads와 동일. 병원이 플랫폼 내에서 응답하지 않으므로 불필요.

---

## 5. 지금 시스템화를 하지 않는 이유

### 5.1. 운영 규모 기준

| 지표 | 현재 상태 | 시스템화 필요 기준 | 비고 |
|------|----------|------------------|------|
| 월 문의 수 | < 50건 | 200건 이상 | 수동 처리 한계점 |
| 협력 병원 수 | < 10곳 | 30곳 이상 | 수동 분배 불가 |
| 운영자 수 | 1-2명 | 3명 이상 | 역할 분담 필요 |
| 평균 응답 시간 | 수동 처리 | 1시간 이내 목표 시 | 자동화 필요 |

### 5.2. 현재 시스템화 시 발생 문제

1. **과도한 자동화**
   - 병원이 시스템에 접속하지 않는데 '병원 알림' 구현은 무의미
   - '리드 자동 배분' 구현해도 운영자가 최종 확인 후 수동 연락

2. **데이터 불일치**
   - hospital_leads 테이블에 기록해도 실제 병원 응답은 전화/이메일로 옴
   - human_touchpoints와 hospital_leads 사이 데이터 동기화 부담

3. **유지보수 부담**
   - 사용하지 않는 기능의 버그 수정
   - 테이블 스키마 변경 시 마이그레이션 복잡도 증가

---

## 6. 다음 단계로 전환하는 명확한 조건

### 6.1. 전환 조건 (AND 조건)

다음 **모든 조건**을 충족할 때 "병원 참여형 시스템"으로 전환:

1. **월 문의 200건 이상** 지속 (3개월 평균)
2. **협력 병원 30곳 이상** 확보
3. **병원 3곳 이상**이 "플랫폼에서 직접 리드 확인하겠다"고 요청
4. **운영자 수동 처리 한계** 명확히 도달 (평균 응답 시간 24시간 초과)

### 6.2. 조건 충족 시 활성화할 기능

| 순서 | 기능 | 선행 조건 |
|------|------|----------|
| 1단계 | 병원 계정 시스템 (가입/로그인) | - |
| 2단계 | 병원 대시보드 (할당된 리드 조회) | 1단계 완료 |
| 3단계 | hospital_leads 테이블 활성화 | 2단계 완료 |
| 4단계 | 리드 자동 배분 로직 | 3단계 완료 |
| 5단계 | 병원 알림 시스템 (이메일/푸시) | 4단계 완료 |

### 6.3. 전환 전까지 유지할 원칙

- hospital_leads 테이블은 마이그레이션 파일만 유지, 실행하지 않음
- `/app/api/admin/leads/*` API는 주석 처리 또는 404 반환
- Admin UI에서 "리드관리(현재 미구현)" 메뉴는 클릭 시 안내 메시지 표시
- 모든 문의 처리는 human_touchpoints 테이블에 기록

---

## 7. 한 줄 요약 (다음 세션용)

**HEALO는 현재 "운영자가 Admin UI에서 문의를 확인하고 수동으로 병원에 연락하는 MVP 단계"이며, hospital_leads 테이블과 병원 계정 시스템은 설계만 존재하고 사용하지 않는다.**
