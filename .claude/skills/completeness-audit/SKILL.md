## 왜 이 스킬이 있나 (2026-07-15, OKKY "Codex 72시간 사이클" 칼럼에서 착안)

우리는 `사고 → 부검(POSTMORTEMS) → 가드 추가`라는 **Worker 루프(고치기)**는 이미 갖췄다. 그런데 **"완성 판정(Manager)"은 아직 사람(PO)의 눈=스크린샷**이라, 같은 부류 미완성이 계속 PO에게 발견된다(칼럼: "인간 attention이 유일한 병목").

이 스킬 = **Manager를 기계로 옮긴 루프.** PO가 보기 *전에* 미완성을 기계가 소진시킨다.

- 채점표(판단 기준) = [`src/lib/completeness/rubric.js`](../../../src/lib/completeness/rubric.js) (사람용: `docs/DEFINITION_OF_DONE.md`)
- 이 스킬은 **범위 한정 regex 가드가 못 잡는 사각**(같은 부류가 "그물 밖 다른 통로"로 재발 — #73·#81·#94)을 *의미*로 메운다.

## 언제 도나
- PO가 "완성도 감사 / 미완성 훑어 / 반쪽 없나 봐줘"라고 할 때
- 큰 UI·플로우 변경을 머지하기 전 (저위험 자동머지 게이트의 확장으로)
- (후속) 주 1회 cron 전면 감사

## 대상 범위
- **기본 = 이번 변경 diff** (`git diff main...HEAD` 또는 현재 미커밋). 좁고 빠름.
- **옵션 = 전면** ("전체 감사"라고 하면): 살아있는 화면·문서 전수. 느리고 비쌈 → PO가 명시할 때만.

## 루프 구조 (Manager → Worker → loop-until-dry)

`rubric.js`의 항목 중 **verify가 `semantic`인 것**이 이 루프의 일감이다(`auto`는 이미 `check:*` CI가, `manual`은 사람이). 골격 첫 타깃 = **유형 3(문서-현실 드리프트)·유형 7(시각 회귀)**.

### 1) Manager 단계 — 미완성 열거 (평가)
대상을 각 semantic DoD 항목의 `done` 조건으로 대조해 **미달 항목**을 뽑는다. 유형별 실측 입력:
- **유형 3 (문서-현실 드리프트)**: `.claude/skills/doc-health/SKILL.md`의 검사 로직을 그대로 재사용 — KNOWN_ISSUES·핸드오프의 "미해결/보류"가 실제 코드(git log + 실제 파일/라우트)와 어긋나는지, 죽은 참조가 있는지. **문서만 읽고 판단 금지 — 근거 대조.**
- **유형 7 (시각 회귀)**: `e2e/content-clip-sweep.spec.ts`를 대상 화면에 돌린 결과(잘림 좌표)를 입력으로. 로그인 뒤편 백오피스·ru/kz 변형은 스윕 밖이므로 여기서 `read_page`(구조·텍스트)·`javascript_tool`(계산된 스타일)로 보강. ※ 예전에 적혀 있던 `preview_eval` 은 존재하지 않는 도구다(2026-07-27 정정).
- **유형 2·6 (조용한 실패·cron 0)**: 변경이 이 성격이면, "성공을 상태코드·DB로 실측했는가 / 같은 가정 쓰는 다른 소비자를 전수 봤는가"를 코드 추적으로 확인.

각 미달을 `{유형, 항목id, 위치(파일:라인 or 화면), 무엇이 미완성인지, 근거}`로 기록.

> 규모가 크면(전면 감사) Manager를 유형별 병렬 subagent로 fan-out. `general-purpose`/`Explore` subagent에 "이 rubric 항목으로 이 범위를 감사하라"를 주고 결과를 모은다.

### 2) Worker 단계 — 전수 수정
미달 항목별로:
- **(a) 수정안** 을 만든다. 저위험(오타·문구·명백한 잘림·문서 종결)은 골격 단계에선 **수정 제안 리포트**까지(자동 커밋은 안정 후). 문서-현실 드리프트의 "사실 교정"(이미 해결된 항목 닫기)은 doc-health 원칙대로 바로 고쳐도 됨(문서만 = 저위험).
- **(b) 전수 스캔**: POSTMORTEMS 2단계 규칙 — "같은 부류가 다른 데 더 없나" 반드시 전수 확인(#73·#81이 이걸 안 해 재발). 발견되면 미달 목록에 추가.
- **판단 필요**(방향이 바뀐 건지, 큰 리팩터가 필요한지)면 고치지 말고 `AskUserQuestion` 버튼으로 PO에게(한 번에 2~3건).

### 3) loop-until-dry
Worker가 새로 건드린 곳 때문에 미완성이 또 생길 수 있으니 **Manager를 다시 돌린다. 2라운드 연속 무발견이면 종료**(상한 3라운드 — 넘으면 남은 걸 리포트하고 PO에게).

## 마무리 (필수)

[`docs/audit/COMPLETENESS_LOG.md`](../../../docs/audit/COMPLETENESS_LOG.md) **최상단**에 엔트리 추가:

```
## YYYY-MM-DD 완성도 감사 (범위: diff|전면)
- 스캔: 유형 N종 / 발견: 유형3 N·유형7 N·… (합 N건)
- 수정: (고친/제안한 것 1줄씩) / 보류: (PO 판단 대기)
- 라운드: N (무발견 도달)
```

보고는 3줄(발견/수정/보류)로 짧게. 진짜 결정이 필요할 때만 버튼으로 PO 호출.

## 원칙 (어기지 마라)
- **정직**: 실측 못 한 유형(manual — 실기기·실메일)은 "검증 못 함"으로 명시. "됐어요" 남발 금지.
- **rubric이 SoR**: 감사 중 "이 유형은 이제 자동으로 잡을 수 있겠다" 싶으면 `check:*` 가드로 승격 제안 + rubric의 verify를 `auto`로. 반대로 새 미완성 부류를 발견하면 rubric에 항목 추가(+ `docs/DEFINITION_OF_DONE.md` 같이 갱신 — `check:completeness`가 드리프트를 막는다).
- **범위 한정 경계**: 이 루프의 존재 이유는 regex 가드의 "그물 밖 통로"를 메우는 것이다. "가드 통과했으니 됐다"에 안주하지 말고 *의미*로 봐라.
