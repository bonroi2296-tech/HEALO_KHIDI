## 현재 상태 (자동 수집)
- 브랜치: !`git rev-parse --abbrev-ref HEAD`
- 최근 커밋 8개: !`git log --oneline -8`
- 미커밋 변경: !`git status --short`
- 최근 5커밋에서 바뀐 파일: !`git diff --name-only HEAD~5 2>/dev/null | head -25`
- 직전 핸드오프 이후 커밋: !`git rev-list --count $(git log -1 --format=%H --grep=핸드오프 2>/dev/null)..HEAD 2>/dev/null`

## 할 일

위 git 상태 + 이번 세션 대화를 근거로, **`docs/PROJECT_CONTEXT.md` 최상단에 새 핸드오프 블록을 추가(또는 갱신)**하라.

⚠️ **새 핸드오프 파일을 만들지 마라.** `PROJECT_CONTEXT.md`가 단일 진실 공급원(single source of truth)이다. 흩어진 핸드오프는 다음 세션을 혼란시킨다(과거 사고 원인).

### 🧹 0. 이번 대화가 비었거나 「밀린 걸 정리해줘」면 — 되묻지 말고 git 기록에서 소급 복원하라 (2026-07-30 PO 요청)

**PO 가 *"오늘 컨디션이 안좋아서 핸드오프 제대로 안했는데 알잘딱 정리해줘"* 처럼 말하면, 「무슨 작업 하셨죠?」를 되묻지 마라.** 아픈 사람에게 되물으면 그게 일이 된다. 기록이 전부 남아 있어서 되물을 필요가 없다:

0. 🔴 **작업본 목록은 `git branch -r` 로 「전수」를 뽑아라 — 세션 시작 훅의 「열린 작업」 목록을 전부로 착각하지 마라.** 2026-07-30 실측: 훅이 띄운 **8개**만 보고 정리했는데 실제 원격 작업본은 **21개**였고, **빠뜨린 것 중에 그날 작업(신청서 없는 작업본)이 있었다.** PO 가 *"오늘 그거만 했어? 더 한거 있었을텐데"* 라고 되물어서야 발견했다. 훅은 **최근 것만** 보여준다.
   ```
   for b in $(git branch -r --format='%(refname:short)' | grep -v 'HEAD\|main\|production'); do
     echo "$b | $(git rev-list --count origin/main..$b) | $(git log -1 --format=%ad --date=format:'%m-%d %H:%M' $b)"
   done
   ```
   그다음 **열린 신청서(PR) 목록과 대조**해 「신청서 없는 작업본」을 따로 뽑는다 — 그게 증발 위험 1순위다.
   **닫힌(폐기된) 신청서도 봐라** — 닫힌 이유가 「범위 초과」면 그 안에 **살려야 할 수정이 섞여 있을 수 있다**(2026-07-30 실측: 닫힌 [#1189] 안에 실서비스 사실 오류 정정 1건이 묻혀 있었다).
1. `git log --all --since="<날짜> 00:00" --pretty=format:"%h|%ad|%d|%s" --date=format:"%m-%d %H:%M"` — **그날 모든 작업본의 커밋**을 훑어 작업본별로 배분한다.
2. `git log origin/main..origin/<브랜치>` 로 **본판에 안 들어간 것**을 가른다. 커밋 본문(`%b`)에 그 세션의 근거가 대체로 다 적혀 있다.
3. 열린 신청서(PR) 목록·본문을 **실제로 조회**한다(기억 금지).
4. 그날 세션 중 **인수인계가 없는 것**을 찾아 표로 대조하고, 그것들을 한 블록에 소급 정리한다.

🔴 **우선순위 1번 = 「신청서(PR)조차 없는 작업본」의 맥락.** PR 이 있으면 본문에 근거가 남지만, PR 없는 작업본은 **정리되면 통째로 증발**한다. 특히 그 작업본의 **코드는 이미 본판에 있고 문서만 남은 경우** — 증발하면 *코드는 남고 이유만 사라지는* 제일 나쁜 형태다. 이걸 먼저 본판으로 건져라.

⚠️ **원문을 통째로 복사하지 마라 — 「요약 + 어디 있는지」로 적어라.** 그 작업본이 나중에 합쳐지면 같은 문장이 두 번 들어가 충돌한다.

⚠️ **소급 복원한 사실은 「2차 정보」라고 블록 안에 명시하고, 6번(검증 상태)에 「내가 재실측하지 않았다」를 적고, 5번 1번 항목을 「재확인」으로 두어라.** 남의 기록을 옮긴 것을 내가 확인한 것처럼 쓰면 다음 세션이 그걸 사실로 읽는다.

⚠️ **남의 세션 신청서를 대신 합치지 마라.** 기록 복구가 이 스킬의 일이고 남의 작업 합치기는 아니다 — 상태만 「초안·미합류」로 적고 5번에 올려라.

핸드오프 블록은 다음 7개 섹션으로:

1. **이번 세션 한 일** — 기능/파일 단위 + 배포·머지·PR 상태(번호 포함)
2. **왜 그렇게 했는지** — 커밋 메시지에 안 남는 결정 배경·근거
3. **안 끝났거나 보류** — 무엇 / 왜 보류 / 풀리려면 뭐가 필요
4. **주의·함정** — 반쯤 하다 만 것, 건드리면 깨지는 것, 헷갈리기 쉬운 것
5. **다음 세션이 먼저 할 일** — 우선순위 순서로
6. **검증 상태** — CI/빌드/check:content 통과 여부. **검증 못 한 건 솔직히 "검증 못 함"이라 명시**(됐어요 남발 금지)
7. **다음 세션 첫 프롬프트** — 다음 세션 시작 시 쓸 지시문을 인용블록(>)으로 1개 **문서(PROJECT_CONTEXT)에 적어만 둔다**. 5번(먼저 할 일)을 PO 말투의 명령형으로 압축 + "먼저 PROJECT_CONTEXT 최상단 읽어"를 첫 줄에. ⚠️ **이건 세션 시작 훅(`session-orient.sh`)이 다음 세션에 자동으로 띄운다 — PO에게 복붙하라고 채팅에 내밀지 마라**(PO 명시 요청 2026-06-22: "복붙 프롬프트 나한테 주지 말고 자동화"). 문서에 기록만 하면 자동화로 충분.

### ⚠️ A. 미검증 항목 자동 승격 (필수)
6번(검증 상태)에 **"런타임 미검증 / 직접 클릭 안 함 / 검증 못 함"** 으로 적은 게 있으면,
그것들을 **5번(다음 세션이 먼저 할 일)의 1번 항목**으로 끌어올려라 — *"⚠️ 직전 미검증분 먼저 확인: …"* 형태로.
이유: 미검증이 다음 세션에서 묻히는 게 가장 흔한 사고. 검증 부채는 맨 위에서 갚는다.

### 🎯 G. PO 취향·선호 누적 (필수 — 이번 대화 분석)
이번 세션 대화에서 **PO가 드러낸 취향·선호·성향**(고정 규칙 CLAUDE.md엔 아직 없는 것)을 찾아내라. 예:
- 특정 디자인/카피/이미지에 대한 호불호("이건 별로", "이게 낫다")
- 일하는 방식 선호(옵션 나열 vs 추천 1개, 설명 길이, 확인 빈도)
- "일단 됐다 / 그건 나중 / 이건 중요" 같은 우선순위·종료 신호
- 반복적으로 강조하거나 짜증낸 지점

찾았으면 **`docs/PO_PREFERENCES.md`의 「분류 대기실」(`<!-- ACTIVE:START -->`~`END`) 안에 날짜와 함께 1건씩 추가/갱신**하라.
- **중복 금지**: 이미 있는 항목이면 새로 적지 말고, 더 구체화됐을 때만 갱신.
- **고정 규칙과 분리**: CLAUDE.md/말투훅에 이미 있는 건 적지 마라(중복).
- **승격**: 같은 취향이 3회 이상 확정되면 한 줄로 "→ CLAUDE.md 승격 후보"라 표시(다음에 사람이 올림).
- 새 취향이 없으면 건드리지 마라(억지로 만들지 말 것).

#### 🗂 G-2. 분류 없이 넣지 마라 (2026-07-28 PO 결정 — 필수)

**여긴 창고가 아니라 대기실이다.** 취향을 넣을 때 반드시 항목 맨 앞에 분류 태그를 붙이고,
태그가 가리키는 자리로 **옮긴 뒤 대기실에서 뺀다**. 형식: ``- `[태그]` **(날짜) 제목**: 내용``

| 판정 질문(위에서부터) | 태그 | 옮길 곳 |
|---|---|---|
| 기계가 잴 수 있나? | `[CI]` | 자동검사·훅 — 문서엔 안 적는다 |
| 특정 상황에서만 쓰나? | `[문서]` | `docs/rules/*.md` 또는 스킬 |
| 말투·보고 방식인가? | `[말투]` | `.claude/hooks/plain-korean.sh` |
| 정말 매번 적용되나? | `[규칙]` | `CLAUDE.md` 승격 |
| 규칙이 아니라 사건인가? | `[기록]` | `docs/POSTMORTEMS.md` |
| 아직 못 정하겠다 | `[미분류]` | 다음 세션이 판정 (5건 넘으면 검사 실패) |

옮겨서 대기실에서 뺀 항목은 **「보관」 섹션에 원문 그대로 + "→ 간 곳: X" 한 줄**을 남긴다(삭제 0건).

**끝나면 `npm run check:rules` 를 돌려 통과시켜라.** 태그 누락·대기실 상한 초과·죽은 문서 참조를 잡는다.
왜: 2026-07-28 활성을 75,756자 → 10,746자로 줄였는데 **반나절 만에 14,797자로 되찼고, 범인은 `/handoff` 4번**이었다.
분류 없이 한 통에 부으면 1건짜리 신호가 11건 잡음에 묻힌다.

### E. PR·CI 상태 자동 수집 (6번 보강)
6번(검증 상태)을 적을 때, **열린 PR과 CI(자동검사) 통과 여부를 기억에 의존하지 말고 확인**해 적어라.
GitHub MCP 도구(`list_pull_requests`, `pull_request_read`로 CI status)를 쓸 수 있으면 열린 PR 번호·CI 초록 여부를 사실대로 기재. 못 쓰는 환경이면 "PR/CI 상태 미확인"이라 솔직히 표기.

규칙:
- 날짜는 **절대 표기**(상대 표기 금지 — "어제" X, "2026-06-17" O).
- PO는 비개발자 → **쉬운 한국어 + 용어 병기**(합치기=머지, 작업본=브랜치 등).
- 기존 최상단 핸드오프가 이미 있으면, 날짜가 더 최신인 새 블록을 그 위에 추가한다(과거 블록은 보존).

### I. ⚠️ 병렬 세션 충돌 방지 — "같은 날"이어도 기존 블록 문장은 절대 고치지 마라 (필수, 2026-07-08 반복충돌로 추가)
**같은 날짜에 다른 세션(병렬 창)이 이미 핸드오프 블록을 써놨어도, 그 블록의 기존 문장을 편집하지 마라 — 항상 그 위에 완전히 새로운 블록을 하나 더 추가하라.** "날짜가 같으니 이어 쓰자"고 기존 블록 안의 문장(1~7번 섹션)을 고치면, 다른 세션도 동시에 같은 문장을 고치고 있을 확률이 높아 **머지 시 충돌**(실제로 2026-07-08에 두 세션이 같은 블록을 동시에 고쳐 충돌 발생·수동 해소함)이 난다.
- **직전 블록 내용이 이미 틀렸거나(예: "미머지"라 썼는데 그새 머지됨) 낡았어도**: 그 문장을 지우거나 고치지 말고, **새 블록에 "📝 정정: 이전 블록의 X는 실제로는 Y임"** 한 줄만 추가해라.
- 블록 제목에 **날짜만 말고 세션 성격을 구분되게** 적어라(예: "2026-07-08 — 밀린 핸드오프 소급 기록" vs "2026-07-08 — 방치 브랜치·OpenUI 검토" 처럼 같은 날짜라도 다른 제목) — 다음 세션이 두 블록을 헷갈리지 않게.
- **커밋 직전 `git fetch origin main && git log origin/main -3`으로 그 사이 다른 세션이 이미 핸드오프를 merge했는지 먼저 확인**하는 습관을 들여라 — 미리 알면 애초에 기존 블록을 건드릴 생각을 안 하게 됨.
- 이렇게 "새 블록만 추가, 기존 블록 불변"을 지키면 git이 대부분 자동으로 합친다(같은 문장을 안 건드리니 충돌 표면 자체가 없어짐). 그래도 두 세션이 정확히 같은 순간에 푸시하면 사소한 위치 충돌은 날 수 있으나, 그건 두 블록을 순서만 맞춰 다 살리면 되는 수준이라 오늘 같은 문장 단위 수작업 병합보다 훨씬 가벼움.

### F. 마무리 검사·회전 (필수 — 다 쓴 뒤)
핸드오프 블록을 다 쓰면 **반드시 아래 2개를 돌려라**:
1. `npm run check:handoff` — 7칸·절대날짜·상대표기 자동 검사. 실패하면 고쳐서 통과시킨다.
2. `npm run handoff:rotate` — 핸드오프가 3개 이상 쌓였으면 가장 오래된 걸 `docs/archive/`로 자동 보관(본문 군살 방지). 2개 이하면 자동으로 아무것도 안 함.

다 끝나면 **변경 요약 3줄만** 채팅에 보고(핸드오프 갱신/PO취향 추가분/검사·회전 결과).

### 🔁 F-2. 신청서는 «자동머지를 걸어» 스스로 사라지게 하라 (필수 — 2026-09-04 PO 지적)

핸드오프를 올릴 때 **신청서를 열어 두고 끝내지 마라.** 올린 즉시 자동머지를 건다:

```bash
gh pr merge <번호> --auto --squash
```

**왜:** 2026-09-04 하루에 핸드오프 신청서가 **6개** 쌓였다(#1604·1605·1607·1608·1609·1610). 전부
같은 파일(`docs/PROJECT_CONTEXT.md`) 한 개를 고치는 것이었다. 자동머지를 건 것은 검사가 끝나는 대로
저절로 합쳐져 사라졌고, **안 건 것만 열린 채로 남아** PO 눈에 「세션마다 뭔가 계속 돌고 있다」로 보였다.
PO 지적: *「09번은 왜 모든 세션이 ci 돌리고 있는거야 한명이 해야 하는거 아냐?」*

🛑 **핸드오프를 「세션마다 하지 마라」로 읽지 마라 — 그건 그대로 유지한다.** 세션이 도중에 죽으면
기록이 통째로 증발하므로 세션별 핸드오프는 필요하다. 고칠 것은 «신청서가 열린 채 쌓이는 것»뿐이다.

⚠️ 검사가 문서 변경에도 도는 것은 **그대로 둔다.** 끄면 안 되는 이유가 둘이다 —
①CI 안에 문서 검사가 들어 있다(`check:content`·`check:rules`·`check:branch-handoffs`)
②필수 검사인 `Smoke Tests (PR)`가 `e2e.yml` 안에 있어서, 그 파일에 `paths-ignore` 를 걸면
**신청서가 영영 머지 안 되는 상태**가 된다. 저장소가 공개라 실행 시간은 무료다(2026-09-04 실측).

### H. ⚠️ 복붙 프롬프트를 PO에게 내밀지 말 것 (PO 명시 요청 2026-06-22)
**다음 세션 첫 프롬프트(7번)는 문서에만 적고, 채팅에 "이거 다음 세션에 붙여" 식으로 내밀지 마라.**
- 이유: 세션 시작 훅(`session-orient.sh`)이 핸드오프의 "다음 세션이 먼저 할 일"을 다음 세션에 **자동으로 띄운다** → PO가 직접 복붙할 필요가 없다. 매번 복붙 프롬프트를 들이밀자 PO가 "자동화하라고 했는데 왜 또 그러냐"고 함.
- 과거엔 반대 규칙(매번 채팅에 띄워라)이었으나 자동화(훅)로 대체됨. 마무리 보고는 위 F의 "3줄 요약"으로 끝낸다.
